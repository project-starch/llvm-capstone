# pgcrypto session-key overflow (CVE-2026-2005)

Upstream commit `7a7d9693c7`, "pgcrypto: Fix buffer overflow in
`pgp_pub_decrypt_bytea()`". It postdates the 17.5 pin, so the pin is affected.

Upstream's own account:

> `pgp_pub_decrypt_bytea()` was missing a safeguard for the session key length
> read from the message data, that can be given in input of
> `pgp_pub_decrypt_bytea()`. This can result in the possibility of a buffer
> overflow for the session key data, when the length specified is longer than
> `PGP_MAX_KEY`, which is the maximum size of the buffer where the session data
> is copied to.

## Established on the pin by inspection

`contrib/pgcrypto/pgp-pubdec.c`:

- `:217` -- `msglen = m->bytes - (msg - m->data);` -- a length that comes out of
  the message the caller passed in.
- `:227` -- `ctx->sess_key_len = msglen - 3;` -- no check against anything.
- `:228` -- `memcpy(ctx->sess_key, msg + 1, ctx->sess_key_len);`

`contrib/pgcrypto/pgp.h`:

- `:112` -- `#define PGP_MAX_KEY (256/8)`
- `:171` -- `uint8 sess_key[PGP_MAX_KEY];` -- 32 bytes, inline in `PGP_Context`.

The fix inserts the guard that is absent at the pin:

```c
sess_key_len = msglen - 3;
if (sess_key_len > PGP_MAX_KEY)
{
    px_debug("incorrect session key length=%u", sess_key_len);
    res = PXE_PGP_KEY_TOO_BIG;
    goto out;
}
```

## Why it is nested

`PGP_Context` is allocated at `contrib/pgcrypto/pgp.c:193` with
`ctx = palloc0(sizeof *ctx)`. `sess_key` is an inline array inside it, so the
copy first runs off the field into the rest of the struct, then off the struct
into the rest of its aset chunk, then out of the chunk. Where it stops is set
by the length in the message, which the attacker chooses.

## Trigger

`trigger.sql` holds upstream's own regression input, copied unchanged from
`contrib/pgcrypto/sql/pgp-pubkey-session.sql` as that commit added it. The data
was generated by `contrib/pgcrypto/scripts/pgp_session_data.py`, which the same
commit adds and which documents how the message is assembled. Using upstream's
data rather than our own keeps the question "does this input really reach the
defect" out of our hands.
