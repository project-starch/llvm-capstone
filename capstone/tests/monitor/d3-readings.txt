Arm A is the positive control. Had it not trapped, this build would not be delivering the exception
and arm B's clean return would say nothing about the fix.

Arm B0 exists because the replacement stores through a CAPABILITY and is therefore bounds-checked,
where the old integer base was not. The monitor's store lands at frame_base + slot*8 for slot 0..31,
and the SAVE_REG sequence that runs first on every trap writes slots 1..31 through the same register
-- so those are already proved in bounds by code that precedes it. Slot 0 is the one address this
change newly subjects to a check that nothing else exercises, reachable when the emulated
instruction's rd is x0. Arm B0 reproduces that geometry exactly, cursor 16 BELOW the base as the
monitor's is, and the access lands on the base itself.
