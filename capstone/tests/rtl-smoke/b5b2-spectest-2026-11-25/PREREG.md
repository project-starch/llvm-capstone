# b5b2-spectest-2026-11-25: SPEC CPU2017 test inputs on B5b-2 Linux (pre-registration, boot 5 first)

The first SPEC rows on the trap route. Each benchmark is a `.dom` started by the trap-route kernel's
`sublet.dom_binfmt` loader from a tmpfs cwd. Boot 5 is the loader's proof on silicon: a known control first, then
the four smallest benchmarks of the B5T arm. Later boots of the same kit carry the rest and the other two arms, each
pre-registered as an amendment here before it runs.

## Platform (as b5b2-linux-2026-11-25 boot 2, which read P1-P4 on board 2)

- bitstream 904cd9c6b, resident on boards 2 and 3, no flash;
- firmware: caplifive-opensbi trap-route-keep-tags eb85e21c, keep-tags on;
- kernel and DTB: unchanged from boot 2's recipe. The kernel is relinked only for this initramfs;
- `make-payload.sh` (here) builds the image: the board's rootfs.cpio unchanged, plus this boot's overlay packed
  root-owned. Image `fw_payload.bin` `222cfdc50fa3…` (19,560,456 bytes, under the 26,000,000 cap); all hashes are in
  `SHA256SUMS.boot5` and `overlay-files.boot5.sha256`.

## The arm

B5T, the compiler lane's bring-up arm (llvm capstone tests/b5b2-illegal-scan history note; dev 937208e0991f):
- runtime: origin/trap/eval ed8cc375c2b1;
- compiler: llvm-c9 29027126f39b with the Full arm's flags;
- ILLEGAL 0 and DELIN 0 in every image.

It is **not comparable to the paper's Full rows**: its allocator is not the measured one (that arm is B5TL1). Its stage
directories are the P1 kits' own `run.sh`, generated by `ports/spec-cpu2017/board/make-stage.py`, unchanged. Image
sha256 prefixes match compiler's list: mcf 75bbd17e, lbm 906d7c73, nab 82f8fd37, xz 2e4bd52c, plus the control
`smoke.dom` 8a464c11 (trap/eval's smoke, QEMU reading "ok", exit 7).

`/init` (`init-boot5`) is compiler's twin init with one change: the per-stage bound is 3,600 s instead of 540 s, because
the board is slower than the bound was sized for. Its no-probe list is empty.

The `capstone_vm` counters the stage prints read `absent` on this kernel; that is expected, not a reading.

## Amendment 1 (2026-11-25, while boot 5 runs): the chain of the other 11 images

**Gate.** The chain starts only if boot 5 reads `TRAPTEST: control smoke.dom rc=7`. If it doesn't, nothing here runs.

**Board.** All of it runs on board 3, the board of boot 5, so every arm of a benchmark is read on one board.

**Order.** One image per boot, in this order: B5TL0-g1, B5TL1-g1, B5T-g2, B5TL0-g2, B5TL1-g2, B5TL1-g3, B5TL0-g3,

stages are in `SHA256SUMS.chain`; every overlay file is in `overlay-files.chain.sha256`.
- Each image is `make-payload.sh` over smoke.dom, an empty probe list, `init-boot5` (byte-identical) and that group's
  stage directories from compiler's `board-stages/<ARM>/<bench>` (MANIFEST.json; images ILLEGAL 0 / DELIN 0).
- The groups: g1 = lbm, mcf, nab, xz; g2 = x264 (its ldecod helper is a plain RISC-V binary), imagick (its
  imagevalidate_538 is plain); g3 = gcc; g4 = perlbench (natperl is plain).

**Predictions, every boot:**
- C `control smoke.dom rc=7`;
- each stage `@@SPEC-END rc=0` and a specdiff pass, by compiler's `run-stage.py read`, the tool boot 5 is graded by;
- `up1 - up0` per stage as a first reading.

**Classification.** As for boot 5. A failed C voids that boot only. A stage whose image differs only by arm and whose
specdiff fails in one arm alone is a finding about that arm.

**Arms and their comparability.**
- B5T: bring-up, not comparable.
- B5TL0: the measured allocator minus mapping reuse.
- B5TL1: the measured allocator with the CRENEW mapping cache. Its residuals are the mprotect hook never firing, the

None of these rows is a cost against Plain yet. They are the first functional and timing readings of the trap route on
silicon, and the matched baseline for the next bitstream (4(b) and the store-drain fix).

## Amendment 2 (2026-11-25, after boot 5 went silent)

**Boot 5** (board 3, `222cfdc5…`): the console grew by one `TRAPTEST: tick` line every 120 s from 04:58Z to about 05:44Z,
which is consistent with the first stage (mcf, first by glob order) computing. Then nothing, for over 70 min. A wedged
kernel or hart and a dropped console stream cannot be told apart from the runner. The board lane is taking the wedge
snapshot through the debug apertures before any reset, then replaying the console. Its reading is recorded when it
lands, attributed to nothing until read.

**The gate.** nested's B5b-2 boot A (board 2, de6399c1dfff) read its own `control smoke.dom rc=7`, the same control
image on the same loader path. That proves the loader on silicon, so the chain's gate is satisfied by that reading
instead of boot 5's.

**The ordering rule.** mcf is the stage boot 5 went silent in, so any image carrying it runs mcf LAST:
- B5TL0-g1 and B5TL1-g1 are rebuilt with `init-ordered`, which is `init-boot5` plus one change: the stage list comes
  from `/stages.order` when present. Their order is lbm, nab, xz, mcf;
- B5T-g1r is added: boot 5's four stages, byte-identical, in that order, to read B5T's lbm, nab and xz.
All three are in `SHA256SUMS.chain2` and `overlay-files.chain2.sha256`. The g1 images of Amendment 1 are withdrawn.

**New chain order** (board 3): B5T-g2, B5TL0-g2, B5TL1-g2, B5TL1-g3, B5TL0-g3, B5T-g3, B5T-g4, B5TL0-g4, B5TL1-g4,
then B5T-g1r, B5TL0-g1, B5TL1-g1. The g1 images go last, since each ends in mcf.

**Silence stop** (the board lane's runner): if the capture grows by 0 bytes for 20 min while /init's 120 s tick is
expected, read the wedge snapshot, end the boot and keep its capture. The stage it was in is then STALL / NO READING.
Predictions are otherwise as in Amendment 1.

**What a stall would read as:**
- an mcf stall in every arm: a property of mcf on B5b-2;
- stalls at a similar uptime in images without mcf: time-based (M-16-like hazards are per allocation, and the uptime
  should then be checked);
- a stall in one arm only: that arm's.

## Amendment 8 (2026-11-25, before a5c45a46d is sealed): what an mcf reading can say

**Readings.** B5T-g1r on board 3 (904cd9c6b, chain 3): mcf ran its whole 3,600 s with the kernel alive, as on board 2
(88db40027). Boot 5 on the same board and bitstream went silent 2,766 s into mcf. The wedge is intermittent: 1 in 2
boots that reached that point on 904cd9c6b, 0 in 1 on 88db40027.

**Correction to Amendment 7** (the board lane's point, adopted):
- An mcf completion on a5c45a46d is CONSISTENT with R-80's fix, not evidence for it, since mcf did not wedge on
  pre-fix bitstreams either.
- The discriminating pair is rtl's ldcexc2: it must wedge on 28fcbb646 (board 2, the positive control) and complete
  on a5c45a46d. If it completes on 28fcbb646 too, it discriminates nothing on silicon, and that is recorded.
- "A silent mcf wedge on a5c45a46d refutes R-80 as mcf's mechanism" stands.

**A new prediction**, written now: mcf has no faulting instruction on the twin (it ran to its end with no fault
line, and its untagged count is 0). So the faulting LDC that S-35 needs on silicon must be a silicon-only exception.
The candidate is R-77's verdict-probe timeout, which denies with 25, and timing makes it intermittent. If that is the
mechanism, then on a5c45a46d, where the excepting LDC now writes back and pops, an mcf that would have wedged instead
**faults with cause 25 at an LDC**. That is a named fault, and it would also be the first silicon instance of R-77 on
Line B. So:
- a cause-25 fault at an LDC in mcf on a5c45a46d supports R-80 + R-77 as the pair;
- a completion is consistent with either;
- a silent wedge refutes R-80.

## Amendment 14 (2026-11-26, before the rows it covers are read): grade-spec-chain-v2.py is binding for every row not yet graded

**Why.** The board lane measured how the console interleaves with SPEC's in-band blocks (board/meas-pw 5106037bcc89,
`b5b2-inband-interleave-2026-11-26/`). On the slow UART, a kernel line or a TRAPTEST tick can land inside a
@@SPEC-FILE or @@SPEC-HASH block. v1 (grade-spec-chain.py 4fa95eaf) undoes only @@HB lines, so:
- a foreign line inside a FILE block crashes the decode and reads MISS. That is a loud false MISS.
- a line split inside a HASH block is silent: the tail parses as a truncated hash. On t1.c it read e750101d…, not
  de7b86d7…, and the stage still passed. Under Amendment 13 the same splice would read x264 as a false MISS.
A scan of all 27 board SPEC captures and the twin's x264 found whole tick lines inside hash blocks in five captures.
Whole lines are dropped harmlessly, so no reading made so far changed. No foreign line was found in a file block, and
no split line anywhere.

**Rule.**
- grade-spec-chain-v2.py is the binding grader for every row of Amendments 9-13 that is not yet graded when this
  amendment is pushed. This covers SP-B5TL1-g1b (booting on board 1), SP-B5TL1-x264b, and every remaining board-3
  row, x264b included. The runnable copy has sha256 b976d2884c8c42d5bf85a24ce4d8507ccf8b0c489b192eff8d6965a834ab2f82,
  and the committed copy differs only in its host path.
- v2 removes "[ <t>] …" and "TRAPTEST: …" lines with their newline inside FILE and HASH blocks only, so split
  lines rejoin. gzip's CRC32 then checks each file.
- A residual foreign line in a block makes the stage NO READING, never MISS. v2 prints "INBAND <stage>: k removed"
  when k > 0.
- v1 runs beside it on the same capture, and is recorded. Any verdict difference between them is reported row by
  row. Rows already graded keep their v1 verdicts.
- v2's controls are the evidence that it fires: the seven splice shapes read PASS with step.txt equal to the clean
  slice, a '$' corruption reads NO READING, and 12 of 14 real captures give byte-identical output.
- Not covered, as v2 says: a corruption inside the base64 alphabet still fails the CRC and reads MISS.
