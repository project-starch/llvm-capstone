== WHAT THIS ESTABLISHES ==
  On this bitstream, N=1 per arm, a revoked alias to leaf[0] is refused (cause 25), while a live alias to
  the same leaf at the same address is not, and neither are ~43k earlier live accesses. The same images
  on 054cea69b read live data through the revoked alias. The defect this folder reports -- a revoked
  reference that reads the current occupant's data -- no longer reproduces on this probe.

== LIMITS -- what these lines do NOT establish ==
  - WHY it was denied. The oldest ids have been reissued thousands of times (reuses_since 2706/1353), and
    the cache holds 256 entries under a 30-bit compare, so deny-on-miss is the EXPECTED route. The hit-dead
    arm (observed revocation) is shown in simulation only (results/sim-rotate-stale.result-lines.txt).
    The two stay confounded with residency here: the live alias was minted recently and would hit.
  - Which k trapped (0 or 21648). If k=0 was allowed, a reference that stale still reads -- not settled.
  - N=1 per arm; neither boot had a closing control.
  - The cross-reflash pairs share image hash, monitor and buildroot, but NOT fw_payload (stale
    741913660fc9 -> edf259ada40a; live 5eeee0ff3390 -> d6038a84b658), and the new stale boot ran the ladder
    first. They are close pairs, not one-variable pairs.
  - The stale WRITE was never reached on silicon, because the read trapped first. Write refusal is shown in
    simulation only (results/sim-rotate-stale.result-lines.txt, arm C).
  - False denies from deny-on-miss under a large live-id population (e.g. SQLite) are untested on silicon.
  - Discriminator, if needed: a k=43295-only variant (just revoked, likely still resident as dead) against a
    live alias installed more than 256 fills earlier and untouched since (a probable miss). If the live one
    traps 25, the denial is selecting on residency, not revocation.
