# S-23's data face on silicon: every instance in one table

**What this folder is:** the kernel's own data loads refused by the CPMP although a loaded RWX entry covers them, on
vp2 bitstreams. **Siblings:** S-23's FETCH face (an S fetch refused after a CSRUNV or CSRETIRE return, worked around by
the monitor's fetch retry, FRTY), shown on silicon from a stale translation alone by the RTL lane's `sv-fetch` arm
(`capstone/tests/rtl-smoke/satpstale-bare-2026-10-19/`); and S-29 (no satp flush; that same folder). The registry entry is
`capstone/docs/ref/ISSUES.md` S-23.

extracted by pattern. N=1 per row; every boot UNGATED (PREFLIGHT=0).

"Seconds" is the Oops's kernel timestamp. The time since the last CSRUNV is not recoverable: no capture prints it.

**What all four share:**
- **The entry.** CPMP slot 7 holds region 21, [0xAC100000, 0xC0000000) RWX, loaded. CPHT 7 means M, reading the
  CSRs afterwards, finds that loaded entry covering mtval. MTVL is a physical address inside it.
- **The kernel side.** The refused access is a kernel load through the linear map: a3 or a5 = 0xffffffd83c2..., with
  badaddr = mtval. Cause 5, in interrupt, then a panic.
- **The monitor's tags.** `CPMX:00000002` and `INJS:00000002` are both the constant CAPSTONE_NO_CPMP_REGION; neither
  names the failed allow term.
- **A fetch retry first, in the same step.** On tree A it comes immediately before the dump, with 0 console lines
  between. On bf3db3175 it comes 18 lines before, with only the next context's image grants (CAPSTONE_VM_ADD_OK) in
  between.
  - On tree A both FRTY pcs are `vm_ioctl+0xab0`, the instruction after the module's CSRUNV; the module base differs
    per boot, the offset does not.
  - This ordering is an observation. Its relation to the refusal is not established.

**Every FRTY is the instruction after the module's CSRUNV in `vm_ioctl`.** The page offset of each pc is matched to
the instruction after a CSRUNV (funct7 0x24) or CSRETIRE (funct7 0x53) in that run's module .text, and named by the
enclosing symbol. Exactly one candidate matched in each module:

| pb10-fix6b | d71f207a | 00F14164 | `vm_ioctl+0xac4` (CSRUNV at .text+0x4160) |

- The method recovers tree A's `vm_ioctl+0xab0`, which a claim-auditor had derived independently.
- **The FRTY handler is the first candidate** (the runtime lane, 2026-10-19): it reads and writes back every CPMP
  entry (`sbi_capstone.c:3490-3533`, capstone-sbi 007d81d), slot 7 included, then sfence.vma and fence.i, right
  before each refusal. The RTL lane is simulating it.

**Two addresses:**
- **0xBC2C0825, three times** (pb10, pb10-fix6b, sql0-treeA): `mod_node_page_state+0x40` from `unpin_user_page+0x2a`,
  `lb a3,0(a3)` (insn 00068683), a3 ffffffd83c2c0825. That is two bitstreams, three modules, two programs, and Images
  that differ.
- **0xBC2B9440, once** (tree A step 4): `_raw_spin_lock_irqsave+0x56` from `__wake_up_common_lock+0x4e`, `lhu
  a4,0(a5)` (0007d703). That is CPU 0's per-CPU `__mmiowb_state`; the decode was checked against that boot's running
  Image by a claim-auditor.
- **Both lie in CPU 0's per-CPU unit:** [PA 0xBC2B8000, 0xBC2C7000), u61440, in tree A step 4's kernel. 0xBC2C0825 is
  that unit's offset 0x8825, in its dynamic area. The same PA from different Images says the unit's base is the same
  across these kernels. That is consistent, not shown per boot.

**What is open:**
- **The mechanism.** The RTL lane's candidate is a revocation walk's late broadcast clearing slot 7's per-entry
  revnode validity (index-only compare), re-armed by the next ADOPT.
- **The discriminator for persistence:** in tree A step 4, die()'s own spin_lock_irqsave re-read 0xBC2B9440 through
  slot 7 with no second refusal. That refutes a persistent deny only if no namespace flush fired across the S/M round
  trip, which depends on srevroot_q at the fault.
- **The arms.** The RTL lane's transient arm comes first. A software workaround (the module flushing the CPMP trackers
  by an srevroot write after each CSRUNV return) is being evaluated from the source, to be tested on sql0's image.
- **What each last context was doing:** sparse-churn retires and re-derives constantly; pb10 is a Sublet pool arm;
  postgres was in its first session (preflight-00). Whether each had a revocation walk in flight is not shown.
