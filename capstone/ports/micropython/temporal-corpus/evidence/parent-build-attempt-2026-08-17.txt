How to build a parent commit, and what it took to find out. 2026-08-17.

CORRECTION. An earlier version of this file concluded that parent builds were
blocked by toolchain age and should be retried "in a container with a
period-correct compiler". That conclusion was wrong, or rather it was right about
the cause and needlessly pessimistic about the cost: gcc-12 is already installed
on this machine, and with it the build simply works. The recipe is below.

TARGET USED: ce491ab0d1, the parent of 4bed614e707c, which fixes MPY-T02
(CVE-2024-8947) and MPY-T05 (issue 13283). Dated 2024-04-22. Host unix port, no
Capstone involvement.

WHAT WORKS

    git -C $CAPSTONE_TMP_ROOT/micropython worktree add /tmp/capstone/mpy-<name> <commit>
    cd /tmp/capstone/mpy-<name>
    make -C mpy-cross -j16 CC=gcc-12
    make -C ports/unix  -j16 CC=gcc-12 MICROPY_MPYCROSS_DEPENDENCY=
    ./ports/unix/build-standard/micropython <script>

Two details matter and neither is obvious:

  CC=gcc-12. The default gcc 15 rejects the tree on
  -Werror=unterminated-string-initialization, a diagnostic newer than the source,
  and -Wno-error only gets as far as mpy-cross crashing with "uncaught NLR" while
  freezing its own asyncio manifest. gcc-12 has neither problem. Use a compiler
  contemporary with the commit.

  MICROPY_MPYCROSS_DEPENDENCY= stops the port sub-make from relinking mpy-cross
  with whatever flags the port was given, which is what broke the link when
  sanitizer flags were in play.

WHAT DOES NOT WORK, AND IS NOT WORTH RETRYING

  AddressSanitizer plus the MicroPython unix port. Every combination tried ends
  in "FATAL: uncaught NLR" on any input at all, including
  `import sys; print(sys.version)`. -DMICROPY_NLR_SETJMP=1 does not help, with or
  without -Wno-error=clobbered. The same binary built without -fsanitize=address
  runs correctly, so the fault is the sanitizer against this runtime, not the
  build or the commit.

  This cost several rebuilds because the control was run late. Build the plain
  binary FIRST and confirm it runs, then add instrumentation; otherwise a broken
  interpreter is indistinguishable from a broken build.

  It also did not matter. The ASan question, is a sanitizer blind to a
  nested-allocator use-after-free, was answered far more cheaply by a
  twenty-line C model in asan-blindness-2026-08-17.txt, which shows ASan
  reporting an ordinary malloc use-after-free and staying silent on the identical
  defect performed inside one sub-allocated region.

RESULT AT THE PARENT

    extend  len 128 head b'AA'
    slice   len 128 head b'BB'
    exit 0

Both cases named in the fix commit, extending a bytearray from itself and
assigning to a slice from itself, run to completion at the pre-fix commit with no
crash, no diagnostic and no visible difference. That is the reproduction, and it
matches what the fix's author recorded: in default configurations the bug "exists
but has no impact", and it took "valgrind with GC-aware extensions" to see it.

So the corpus records this as executed-and-silent rather than as corruption. The
dangling pointer is internal to array_extend and never surfaces in a Python-
visible value, which is precisely why a nested allocator makes this class of
defect so hard to see: not merely unreported, but unobservable from the language.
