    cincoffset with an UNTAGGED rs1 -- pc=0xf020bee4 rd=x12 rs1=x10 val=0xf0f7e000

boot 3 (same image as boot 2, by mistake: the tree was configured without --enable-depend, so

  and PGSU_CLEAN=1 rebuilds the objects once; run-domain.sh retries (PGSU_ATTEMPTS) and takes

boot 5 (patch 0009: the prefetcher's context as a void *): StartupXLOG completes (the checkpoint
  BootStrapXLOG wrote is read back through the prefetcher), the catalog script is opened
  from /mnt/host/pg-input, and the backend halts on the first Datum that carries a pointer:
    Cap mem access requires capability: pc = f02ea470 (GetTableAmRoutine+0x38), rs1 = x10, value = f0d615e0
    x10 = heapam_methods (.rodata), an integer: OidFunctionCall0(HEAP_TABLE_AM_HANDLER) returned
    PG_RETURN_POINTER(&heapam_methods) as a Datum, and DatumGetPointer gave the address back
    without the capability; the first load through it (IsA(routine, TableAmRoutine)) faults.
  The one caller of GetTableAmRoutine a bootstrap backend reaches before this is none: the
  relcache's init phases return early in bootstrap mode, so this is the catalog script's
  first statement (create pg_proc: heap_create -> RelationBuildLocalRelation ->
  RelationInitTableAccessMethod). Where the boot attempt stops: layer 3, exactly as the plan
  said, and not one line before it.

Patches 0007-0009 are the uintptr_t-as-pointer sites met on the way (TYPEALIGN, one wide
pointer under it, the prefetcher's context); each is a few lines. The Datum is not: a Datum
is returned by every function the fmgr calls, and the fmgr convention is the ABI of the
whole backend. That is the intcap decision, plans/intcap-uintptr-model.md.
