## 1. Headline

**14 of 15 rows reproduce a memory-safety violation. 12 of 15 reproduce the
temporal-borrow class the benchmark is about.**

Three different denominators matter, and conflating them is the main risk when
writing this up:

| Measure | Count |
|---|---|
| Reproduce some memory-safety violation | **14 / 15** |
| Reproduce a **temporal borrow** (use-after-free / use-after-lifetime) | **12 / 15** |
| Reproduce as **spatial** (out of the stated scope) | 2 — rows 6, 11 |
| Do not reproduce | 1 — row 7 |

The companion benchmark note is a temporal-borrow benchmark ("every defect here is a
temporal borrow"; "There is no spatial or single-domain row, by selection"). On its
own terms the number is **12/15**. Quoting 14/15 for it would be a category error.

All 15 rows' `run.sh` currently pass (`PASS=15 FAIL=0`) — each asserts its expected
native and QEMU outcome, so the corpus is scriptable and regressions are detectable.

## 3. Coverage by language pair

| Subject | Rows | Reproduce |
|---|---|---|
| Lua in Rust (rlua) | 1, 2 | **2 / 2** |
| Rust → C (libpulse-binding) | 3 | **1 / 1** |
| mruby (Ruby ↔ C) | 4–15 | 11 / 12 |

The corpus is no longer monolingual, which was its worst structural weakness. The
companion note's "two subjects" framing and its "shown across Lua–Rust and Ruby–C"
conclusion are now backed by working artifacts. All three non-mruby rows are
temporal.

**Diversity remains the weak spot, not count.** Six of the twelve temporal rows are
the same mechanism: native C code holds a raw pointer into the mruby VM register
stack across a callback into Ruby, and the callback grows the stack (rows 4, 5, 8,
10, 13, 15). A mechanism that defends that pattern once defends half the corpus.
The genuinely distinct temporal rows are 1 (GC resurrection frees Rust-owned heap),
2 (Rust retains a managed handle past the state's death), 3 (Rust→C iterator
outliving a C object), 9 (`irep` pool vs. `FSHARED` substring), 12 (`DATA_PTR`
dangling after a `longjmp`), and 14 (GC scanning stale stack slots).

Note also that RISC-V evidence for the temporal class comes from only three mruby
rows (4, 9, 15), since rows 1–3 have no rv64 leg and rows 6/11 are the spatial ones.
Thin if the hardware story leans on it.

## 4. Decisions needed from the core team

### 4.1 Rows 6 and 11 are spatial, not temporal

Both reproduce as `heap-buffer-overflow`, not use-after-free. This was checked, not
assumed:

* **Row 11** (`OP_GETUPVAR` scope-level truncation). The plausible temporal path — a
  dangling `REnv::stack` after a VM stack realloc — is closed at this version by
  `envadjust()` (`src/vm.c:143`), which walks every live callinfo and rewrites
  `e->stack` for stack-shared environments. Two further attempts failed: letting a
  `Proc` escape all 129 scopes and calling it after GC (mruby *closes* the
  environment on escape, copying registers to heap-owned storage, so nothing
  dangles), and forcing reallocation between capture and read (neutralised by
  `envadjust`). The actual defect is operand-width truncation: the level field is 7
  bits, `codegen.c:2191` emits it unchecked, so nesting ≥129 wraps and the VM
  resolves a smaller, wrong environment then indexes it with the outer scope's large
  index.
* **Row 6** (pattern-matching bytecode corruption). A corrupted register operand
  stores past the end of the frame. Nothing is freed and reused.

Neither is addressed by revocation — **bounds** are what stop them. Options, stated
in each row's `target.md`:

* **Keep them, reclassified as spatial.** Honest, artifacts are complete and
  deterministic, but the "all temporal" framing must be softened and the linearity
  argument for these two rows becomes bounds-checking.
* **Drop them from the temporal subset.** Preserves the uniformity claim; the
  artifacts stay as evidence of why they were dropped.

Either way the CVE descriptions' "UAF" characterisation does not hold at these pins.

### 4.2 Row 7 appears not to exist as specified

Three independent problems, each verified against source:

1. **The issue number belongs to row 6.** Upstream `e50f15c1` says "Fixes #6701" and
   changes only the pattern-matching peephole. Searching all mruby history for
   `6701` returns that commit alone.
2. **The named function does not exist in the assigned version.** `mrb_bint_reduce`
   has 0 occurrences in 3.1.0 / 3.2.0 / 3.3.0 and first appears in the 3.4.0 line —
   contradicting spec §5/§6, which place row 7 in the "single 3.1.0 build" Tier-1
   cluster. The row was never buildable as grouped.
3. **The described GC hazard is closed.** The raw `struct RBigint*` locals held
   across an allocating call look unrooted, but `mrb_obj_alloc` (`src/gc.c:468`)
   calls `gc_protect()` on every allocation; nothing in `bigint.c` or `rational.c`
   saves/restores the arena; and `MRB_GC_STRESS` cannot help, because its full GC
   runs inside `mrb_obj_alloc` *after* the previous object was already protected.

A working build (bigint + rational + ASan + riscv64) and a probe trigger are kept, so
only a trigger is missing if the row is real. **Report row 7 as unresolved, not
verified.** The benchmark table currently lists it as a confirmed temporal defect
with a public ASan trace; nothing found supports that. If it is dropped, the
companion note's tally sentence claiming the corpus spans "the bigint gem" needs
amending too.

### 4.3 Confirm the CVE-2026-1979 mapping against NVD

Row 6's identifier and mruby #6701 resolve to the same upstream fix by commit
message. Worth an independent NVD check, since it cannot be verified offline.

## 5. Tooling finding: ASan is structurally blind to row 3's class

Row 3's stale dereference executes inside prebuilt `libpulse.so` /
`libpulsecommon.so`, distribution libraries with no sanitizer instrumentation. ASan
poisons the region on `free()` but only checks accesses it instrumented, so it never
sees `pa_proplist_iterate()` read it and **the ASan build exits 0**. Valgrind
instruments at machine level and catches it.

`xlang/3/asan.txt` therefore holds a valgrind report, with a header explaining why,
and `xlang/3/run.sh` runs both legs so the clean ASan pass is not misread as a failed
reproduction.

**Generalises: for any Rust→C row where the stale dereference lands in a prebuilt C
library, ASan is the wrong tool and a valgrind-class tool is required.** Worth
knowing before similar rows are added.

## 6. Two rows need a vendored toolchain patch

Rows 1 and 2 pin rlua commits that predate changes modern rustc enforces as hard
errors; neither builds at all on any post-2020 toolchain without a patch. Each patch
is applied by `build.sh` and carries a header arguing why it does not mask the
defect:

* **Row 1** — `mem::uninitialized()` → `std::ptr::read` at two sites. **One of those
  sites is the userdata destructor under test**, so the substitution was chosen
  specifically to preserve the double-drop: `ptr::read` moves out and drops exactly
  as `mem::replace(_, mem::uninitialized())` did and likewise leaves the slot
  unmarked, so a second `__gc` still double-drops. This is the one judgement call in
  the corpus that a reviewer should check deliberately.
* **Row 2** — removes a trailing semicolon from the `rlua_panic!` macro body (used in
  expression position). Nowhere near the code under test.

If the corpus must contain only unpatched upstream source, rows 1 and 2 revert to
not-reproducible and the reasoning is already recorded either way.

## 7. Defects found in the original artifacts

Recorded because they indicate how the first pass was produced, and because the
specific mistakes are easy to reintroduce.

* **Row 2 pinned a commit from this repository.** `4be78cb10177` is
  "ladder-perf runner: rebuild doms by default …" from llvm-capstone — not an rlua
  commit. It is not a valid object in rlua at all. The checkout was wrapped in
  `|| true`, so it failed silently and the build used whatever rlua HEAD happened to
  be (v0.20.1, a modern mlua-backed rewrite). Correct pin, derived from the upstream
  fix `0f5a9a3`: **`78021185`**.
* **Row 3 targeted the wrong crate.** It depended on `hlua = "0.1.0"`, a Lua-in-Rust
  binding, while spec §6 and the benchmark table both define row 3 as
  **libpulse-binding** ("Rust→C UAF: iterator outlives the C object it reads").
  Correct pin: **`b6b1010`** (crate 2.4.0, last before the 2.5.0 security fix).
* **Rows 6 and 11 had non-functional triggers.** Row 6's `trigger.rb` was the single
  bare token `EOF` — a heredoc whose body was never written. Row 11's was **Python**
  (`for i in range(2, 500):`), so it died with a Ruby `SyntaxError` at line 2 and
  never exercised nesting; its "128 nested scopes" was a comment over 2 real levels.
* **Rows 1 and 3 had broken scripts.** Both omitted `cd "$DIR"`, so cargo ran in the
  parent directory and errored `could not find Cargo.toml` — masked by `|| true`.
* **Skip rationales did not match reality.** Six of the seven were falsified: the
  parser accepts 129–254 nesting levels (the `too complex expression` limit is 255,
  not 128); the ASan-instrumented interpreter boots fine at `cda2567c` (32 `__asan`
  symbols confirmed); row 14 aborts 10/10 rather than needing "fuzzer-driven heap
  layouts". Only row 1's rationale described a real obstacle — and even that one was
  removable in two lines.

## 9. Reproducing

```bash
cd xlang/<row> && ./build.sh && ./run.sh
```

Each `run.sh` exits non-zero if the expected violation does not appear.

| For | Need |
|---|---|
| mruby rows (4–15) | clang/gcc with `-fsanitize=address`, Ruby + Rake |
| RISC-V leg | `riscv64-linux-gnu-gcc`, `qemu-riscv64`, `/usr/riscv64-linux-gnu` sysroot |
| rows 1–3 | Rust **nightly** (`-Zsanitizer=address`), `llvm-symbolizer` |
| row 3 | `valgrind`, `libpulse-dev` |

Verified with clang 21.1.8, gcc riscv64 cross, qemu-riscv64 10.2.1, rake 13.3.1,
rustc/cargo 1.96.1 + nightly, valgrind, libpulse 17.0. Vendored trees and build
output are gitignored and created on demand; roughly 3 GB fully built.

## 10. Out of scope here

Per spec §9, nothing in `xlang/` uses the Capstone capability compiler,
capability-protected domains, revocation, or the FPGA. Each `boundary.md` closes with
a note on what a capability mechanism *would* do at that row's free site — including,
for row 3, the observation that a capability would catch a fault ASan cannot see
without recompiling PulseAudio — but nothing is implemented. That is Phase 2.
