**Date:** 2026-07-13

## The claim

Paper conclusion, deliverable 2: *"the capability-mediated borrow path stays
close to raw pointers and well below the copy baseline."* Deliverable 1 (the
engine-minted binding) was explicitly **out of scope** — measure, don't build.

## Why an instruction-count proxy (the gated decision)

QEMU is a functional/ISA model: correct instructions and faults, **no**
pipeline/cache/cycle model. So a real timing number is impossible here; a
deterministic **dynamic instruction count** is an honest overhead proxy. The
human selected vehicle (a). The alternative (b) would first require obtaining a
cycle-accurate vehicle. A mislabelled "timing" number on a functional model is a
reviewer trap, so every number is labelled a functional-model proxy.

## What I built

1. **Emulator readout `csrdicount` (`capstone/capstone-qemu`, my lane).** A
   Capstone debug op (opcode `0x5b`, funct3 `0x1`, funct7 `0x48`) that reads
   QEMU's raw retired-instruction count (`icount_get_raw()`) into `rd`
   (decode + `trans_csrdicount` + `helper_csrdicount`; `translator_io_start`
   makes the read I/O-safe and accurate to the current instruction). Under
   `-icount shift=0`, one tick == one retired instruction, so a `csrdicount`
   delta is an exact dynamic instruction count, readable at any privilege
   (unlike `rdcycle`/`rdinstret`, which are gated by `[m|s]counteren`). QEMU
   rebuilt; **gitlink bumped**.
2. **`tests/runtime-qemu/borrow-cost-probe/`.** One domain (`borrow_cost.c`,
   Capstone clang `-O2`) receives a real LINEAR arena via the intra-domain
   `REGION_SHARE`/`REV_TRANSFERRED` path and runs three variants of the same
   borrow-one-word boundary op, each bracketed by `csrdicount`, plus an empty
   calibration loop that is subtracted out:
   - **raw** — dereference the shared word;
   - **borrow** — `mrev` (mint revocation cap) + `delin` (delegate working cap)
     + access + `revoke`, threading the reclaimed LINEAR handle (`revoke`
     returns it) into the next lend so the loop is a valid, repeatable
     borrow/return lifecycle;
   - **copy** — 16-byte-wide `__builtin_memcpy` in fixed 256 B chunks (fair,
     memcpy-quality; no libcall), at 256 B and 1024 B.
   Results reported through the existing `csdebugcount`/`csdebugcountprint`
   counters (land in the serial log).
3. **`--qemu-extra-arg` passthrough in `run-domain-smoke.py`** (additive; default
   empty, no behaviour change) to pass `-icount` on the measurement boot only.

## Results (`-O2`, 1024 iters, deterministic; full note in the probe's RESULTS.md)

| Variant | instr/op | vs raw | model |
|---|---:|---:|---|
| raw            |  2 | 1.0× | O(1) |
| **borrow**     |  6 | **3.0×** | **O(1)** |
| copy 256 B     | 34 | 17.0× | O(payload) |
| copy 1024 B    | 130 | 64.9× | O(payload) |

- **Close to raw:** borrow adds **4 instructions** (`mrev`, `delin`, `revoke`,
  handle-rethread) over a raw load — a small **payload-independent** constant.
- **Well below copy:** borrow is **5.7×** cheaper than a 256 B copy, **21.7×**
  at 1024 B; copy is `2 + payload/8` instr (**O(payload)**, exact fit) while
  borrow/raw are **O(1)**, so the advantage grows with payload size.
- **Dynamic == static:** the `csrdicount` counts match the `-O2` disassembly
  loop bodies exactly (2 / 6 / 34 / 130), as expected for straight-line bodies
  on a functional model — the measurement is sound.

## A fidelity decision worth recording

The monitor-mediated borrow path (ioctl → kernel → SBI → M-mode monitor) would
have measured **Linux syscall scaffolding**, an emulation artifact, not the
hardware mechanism. The paper's "close to raw pointers" is about the **inline
capability ISA sequence**, so the borrow variant executes `mrev`/`delin`/
`revoke` **inline in-domain** (the intra-domain-mrev-revoke substrate), which is
what a hardware borrow compiles to. This is stated in RESULTS.md.

Fairness the other way: the copy baseline uses **memcpy-quality 16-byte
transfers** (buffers 16-aligned), not a pessimistic word loop — so the borrow
advantage is not overstated. A word-granular copy would be ~2× larger; the
conclusion is robust to the copy implementation either way.
