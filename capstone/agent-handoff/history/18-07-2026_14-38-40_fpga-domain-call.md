# Task 017 — domain-CALL stall localized: monitor-software (missing `fence.i`), NOT RTL

**Date:** 2026-07-18
**Branch:** capstone-bootstrap-b
**Scope:** diagnostic + a surgical monitor fix staged as a patch. No RTL /
`capstone-ariane` changes; no SPI/flash writes; no board run this session.

## Verdict (one line)

The Capstone domain-CALL stall on the CapliFive CVA6 is **monitor-software in our
OpenSBI**, not RTL: our `capstone-bootstrap` `sbi_capstone.S` is **missing the 9
`fence.i` icache-flush instructions at the domain-switch/trap boundaries** that
the board-validated `genesys-testing` lineage keeps. Fix applied + staged as a
patch; the confirming board run (rebuild UP built-in `fw_payload` with the patch,
GDB-boot, sweep) is the only remaining step.

## How it was localized (without burning a board slot)

The task's reframe is correct and decisive: **GDB-boot loads OUR `fw_payload`,
whose OpenSBI is OUR build.** So the stalling Capstone SBI path is our binary, and
the monitor-vs-RTL question is answerable from our own tree + QEMU.

1. **The identical monitor completes both probes under QEMU.**
   `tests/rtl-smoke/RESULTS.md`: running the SAME OpenSBI Capstone monitor under
   `virt-capstone`, both the borrow-cost and revoke-cost `.dom` run end-to-end —
   full `cscall`/`csreturn` domain-switch round-trips, region shares, mrev/revoke —
   and print RESULT (bump 7 / norevoke 60 / revoke 65; borrow raw 2 / borrow 6).
   QEMU implements the domain switch in `helper_cscall`/`helper_csreturn`
   (`capstone-qemu/target/riscv/op_helper.c`). **So the monitor C logic and the
   ISA-level domain-switch semantics are correct.** The board stall is therefore
   NOT a monitor-logic bug reproducible in emulation. (The earlier `helper_cslcc`
   assert seen under QEMU is an emulator cap-field-query limitation on a sealed
   cap — unrelated to the domcall.)

2. **What QEMU cannot model: icache/pipeline.** The one thing the functional model
   omits is exactly the class that already bit this CVA6 twice — RFENCE and
   `insmod` both hang on its icache/text-patch coherence path.

3. **Config comparison (Task 3) found the smoking gun.** Diffing our OpenSBI
   (`capstone-opensbi` branch `capstone-bootstrap`, monitor submodule `2f772bb`)
   against the board reference `origin/genesys-testing` (monitor `99aaffa8`):
   - the two monitor lineages have **diverged** (ours carries the newer
     `share_child_region` / clean-fault-delivery work; theirs does not);
   - `genesys-testing`'s monitor tip commit is literally **`99aaffa8 "Added
     fence.i back"` (Jason Yu)** — it re-inserts 9 `fence.i` into `sbi_capstone.S`;
   - **our `sbi_capstone.S` has ZERO `fence.i`.** Our lineage descends from the
     version where they were dropped.
   - (Secondary, noted not applied: `genesys-testing` also comments out the
     `csrs mstatus, MIE` re-enable in `cap_env_init` and the interrupt preamble in
     `sbi_capstone_init.S`. Left alone — `fence.i` is the surgical, purely-additive
     fix that matches the exact failure signature; the MIE change alters timer
     behaviour and is the next thing to try only if fences alone don't suffice.)

## Why this explains every observation

- `create_dom` **succeeds** on the board: it is pure monitor computation
  (`split_out_cap`/`__seal`), no domain switch, no trap-return — the icache is
  never crossed, so no fence needed.
- the **first `DOM_CALL`/`REGION_SHARE` hangs**: it is the first traversal of the
  trap-entry → `handle_trap_ecall` → `return_to_sumode`/`call_into_smode`
  assembly, i.e. the M-mode↔domain/S-mode context switch. Without `fence.i` the
  CVA6 fetches stale icache lines there → the switch never lands → no RESULT.
- **QEMU passes**: no icache model, so the missing fence is invisible.
- same **RFENCE/insmod icache-coherence class** already documented on this core.

## The fix (applied, staged, assemble-verified)

`sbi_capstone.S` in the monitor submodule, 9 `fence.i` re-inserted at the same
boundaries `genesys-testing` uses: trap entry; before `save_smode_context`; the
ecall-vs-non-ecall dispatch; before `handle_trap_ecall`; before `handle_exception`;
the two `j return_to_sumode` paths; and before both `mret` paths
(`return_to_sumode` + `call_into_smode`). Count now matches the reference (9 = 9).

`fence.i` is purely additive (flush stale icache; cannot change correctness, only
a few cycles per switch) → safe to carry as a staging patch. The edited `.S`
assembles cleanly (`clang --target=riscv64 -march=rv64gc`; all Capstone `.insn`
macros + `fence.i` accepted).

**Staged as a patch (not committed to submodule source, per guardrail):**
`capstone/agent-handoff/patches/opensbi-capstone-sbi-domain-switch-fence-i.patch`
The working-tree edit is left in place in
`components/opensbi/lib/sbi/capstone-sbi/sbi_capstone.S` so a rebuild picks it up.

## Remaining step to the confirming board numbers

1. Rebuild the **UP built-in** `fw_payload` (SMP=n + capstone `obj-y`, per
   `fpga-up-image-vermagic`) with the patched monitor — via the `caplifive-system`
   umbrella (`scripts/build-software.sh --mode fpga`) or the prior UP built-in
   scratch recipe. OpenSBI is `OPENSBI_OVERRIDE_SRCDIR` → `components/opensbi`, so
   the edited `.S` is picked up by an `opensbi-custom` rebuild.
2. GDB-boot it (the verified self-serve recipe in `run_rtl_smoke.boot_via_gdb`)
   and run the borrow-cost + revoke-cost sweep.
3. Expect: `create_dom` → the CALL now **returns** → RESULT lines. Parse with
   `run-revoke-cost-fpga-qemu.sh --parse-uart`. Report cycles/op vs the QEMU
   reference (+5 revoke-at-free, O(1)). NB the board's UART RX is lossy — throttle
   input (already handled by `throttled_send`).

If the CALL still stalls with the fences in, THEN escalate: try the MIE/interrupt
change, and only after that treat it as RTL (the CVA6 capability domain-switch
itself) for the owner — with this note as the precise characterization.
