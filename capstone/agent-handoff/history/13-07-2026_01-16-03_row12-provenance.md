## The liability

A's consolidated ledger (`cve-repros/PROVENANCE-LEDGER.md`) flagged row 12 as the
one hard citation-mismatch: the row's essence is a **null-deref** ("ignore
`SQLITE_BUSY` on close, clear the db handle, later deref the NULL handle"), but it
cited **expo/expo PR #34992**, which is a statement-**leak** fix (swaps a manual
`cachedStatements` map for `sqlite3_next_stmt()`/`sqlite3_finalize()` to finalize
open statements before close). Citing a leak-fix PR for a null-deref row is what
makes `tab:scope`'s "All links verified" untrue.

## The search (the crux; do not force a match)

Searched for a real "ignore `SQLITE_BUSY` on close → NULL/stale `sqlite3 *` handle →
later C-level deref" bug across bindings:

| Binding | Upstream found | Verdict |
|---|---|---|
| expo-sqlite | **#34990** (crash) + #34992 (fix) | crash is a **Java NPE**, not a C `sqlite3 *` deref |
| cordova-sqlite-storage | #702 | feature request, no crash/deref |
| better-sqlite3 | #155 | throws on live stmts; no null-handle deref |
| node-sqlite3 | #16/#9/#372/#1764 | surfaces the BUSY *string* to JS; no C null-then-deref |
| go-sqlite3 | #192 / golang#18429 | **Go-runtime** nil panics (double-close/state), not C `sqlite3 *` |
| PHP sqlite3 | #47145 | the BUSY condition, surfaced not derefed |
| SQLite CVE DB | 2018-8740, 2019-9937, 2019-19880, 2020-9327, 2020-13435, 2020-35525 | engine-internal null-derefs, not binding close-while-busy |

**No binding upstream ignores `SQLITE_BUSY`, nulls its C handle, and derefs it in
C.** The hazard is real and widely reported, but every artifact either surfaces
`SQLITE_BUSY` as a handled return code (no deref), crashes in the managed/runtime
layer (expo Java NPE, go nil panic), or is an unrelated engine-internal null-deref.

## Decision: Outcome B, re-anchored — and why not A

The closest genuine artifact is **expo #34990**, the actual crash report that #34992
fixes: a `java.lang.NullPointerException` from `NativeDatabase.closeSync()` after
tab navigation left prepared statements live, where "the database instance is either
uninitialised, already closed, or otherwise invalid at the time of closure." That is
row 12's shape — so the citation is re-anchored from the leak-fix PR to the crash
report.

It does **not** graduate to ✓ literal, and forcing it would repeat the very error
the ledger exists to fix. #34990's observed fault is a **managed-language NPE** on
the JS/Java wrapper, not a C-level dereference of SQLite's own `sqlite3 *`. By the
ledger's bar (✓ literal = the cited artifact is a real *SQLite-pointer*
memory-safety defect), that is *adjacent*, not a lowering — the same honest call
already made for **row 7** (managed-dict GC, not a stmt UAF) and **row 13** (host
`row_factory` deletion, no SQLite C call). Row 12's C repro
(`sqlite3_get_autocommit(NULL)` on the cleared handle) is a faithful **behavioral
translation** of #34990 into the SQLite-pointer domain, i.e. an honest MODEL.

Per the fidelity bar, the fault stays a **null-deref** (oracle `null-deref`) — not
silently converted to UAF. The interesting fidelity point is preserved in the
records: a *failed* `sqlite3_close` (`SQLITE_BUSY`) does **not** revoke the live
connection, so this is not a successful-teardown cascade; the wrapper nulls its
handle anyway and the fault is a genuine null/stale-handle deref.
