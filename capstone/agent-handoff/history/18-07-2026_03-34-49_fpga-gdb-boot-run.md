# Task 017 — GDB self-serve boot WORKS on the real board; sweep blocked by board-level UART loss + a Capstone domain-CALL stall

**Date:** 2026-07-18
**Branch:** capstone-bootstrap-b
**Scope:** additive test tooling (`fpga_driver/`) + our-image rebuilds (kernel:
UP module vermagic fix, then capstone built-in). No monitor/RTL/submodule-source
changes.

## Outcome in one line

The self-serve **GDB boot works end-to-end**: our image loads into DRAM via the
gdb session's OpenOCD and boots OpenSBI → Linux → a **root shell** on the real
board, no owner, flashing nothing. But the perf **sweep does not complete**: (a)
the board's UART RX is intermittently lossy (drops chars, corrupting commands),
and (b) when a `.dom` command does get through cleanly it loads + `create_dom`s
successfully, then **stalls at the Capstone region/CALL operation** — a
monitor/RTL-level limitation on this FPGA, outside our image's scope. **No cycle
numbers obtainable.** QEMU reference stands (bump 7 / norevoke 60 / revoke 65 →
+5, O(1); borrow raw=60/borrow=172 cyc/op under emulation).

## The working boot recipe (verified live, repeatable)

The container can't fetch our image (no download endpoint; no fetch tools; no
shared FS) — but **OpenOCD runs on the host** (a Raspberry Pi), and `monitor`
commands execute there. `monitor exec ls` / `monitor glob *` reveal the console
app dir with an `images/` folder (where uploads land). So, in one gdb session:

```
gdb_start
monitor reset halt                                  # halt at reset vector, M-mode, BEFORE the bootrom reloads SPI
monitor load_image images/<fw_payload> 0x80000000 bin   # OpenOCD reads the HOST file -> DRAM (~116 s for 15 MB)
monitor load_image images/caplifive.dtb 0x82200000 bin  # the DTB the bypassed bootrom no longer supplies
set $pc = 0x80000000 ; set $a0 = 0 ; set $a1 = 0x82200000
continue                                            # OpenSBI -> Linux -> buildroot login:
# log in: root (no password); confirm shell with an echo probe
gdb_stop                                            # detach BEFORE the .doms (domain switch desyncs an attached session)
```

Verified: `x/4xw 0x80000000` → our header `0x00050433…`; DTB magic `0xedfe0dd0`
at `0x82200000`; `uname` → `Linux buildroot 6.4.14 #… riscv64` (OUR UP build, no
SMP). This is wired into the driver as `boot_via_gdb` / `--boot-method=gdb`.

### Load-order facts that matter

- `monitor load_image` (in the attached gdb OpenOCD, core halted) is the ONLY
  path that gets our 15 MB image into DRAM without (i) the console `load-image`
  poisoning the subsequent gdb attach (TAP "examination failed" → gdb commands
  hang) and (ii) the resident boot-loop reloading SPI over `0x80000000`.
- The DTB is mandatory: our fw_payload embeds none, and bypassing the bootrom
  means nothing places one at `0x82200000` → without it Linux has no console/no
  boot.
- Timings: power-cycle + ~25 s settle before load paths; ~20 s settle after
  `gdb_start` or OpenOCD reads JTAG "all ones"; the board wedges if left
  continuously powered.

## Two board-level blockers that stop the sweep (not our image)

1. **`insmod` freezes the board.** `capstone_init()` is trivial
   (`misc_register`), yet `insmod /capstone.ko` hangs the whole board — the
   kernel module loader's icache/text-patch path does not complete on this CVA6
   (same class as the RFENCE boot gap). **Fix (in our image):** build capstone
   **built-in** (`drivers/misc/capstone.c`, `obj-y`) so `/dev/capstone` exists at
   boot with no runtime insmod. New image **`fw_payload_up_builtin.bin` sha256
   `1d7a02e4…`**, QEMU-validated (`crw-rw-rw- 10,127 /dev/capstone` at boot, no
   insmod; borrow `.dom` runs). On the board it confirmed `/dev/capstone`
   PRESENT at boot.
2. **The Capstone domain CALL stalls.** With the built-in image + gdb detached,
   a `.dom` loads and `create_dom` succeeds (kernel prints the domain region:
   `code size = 3776, entry_offset = 0`, `created domain ID = 0`), then hangs at
   the next region/CALL SBI operation — no RESULT after repeated 180–200 s
   waits. This is in the **monitor/RTL** (the Capstone SBI region/call handling),
   which we do not modify. Separately, the UART RX intermittently drops runs of
   characters even throttled char-by-char (`/capstone.ko`→`/capstoneko`,
   `revoke_cost`→`ke_cost`), so command entry itself is unreliable.

## Driver changes (additive, mock-green)

- `boot_via_gdb`: the verified recipe above (host `monitor load_image` for image
  + DTB, set pc/a0/a1, continue, `login_root`, then `gdb_stop`). `boot_board`
  gains `dtb=` (required for gdb). `throttled_send` (char-at-a-time, UART-RX
  overrun workaround) and `login_root` (root, no password, echo-probe shell
  confirm) added.
- `run_smoke` gains `load_module=False` for a built-in-capstone image (insmod
  hangs this board). Mock + `test_dryrun` updated to drive the load_image + login
  path; `python test_dryrun.py` green.

## What remains / hand-off

Getting the cycle numbers now needs a **board/monitor-side** fix, not our image:
the Capstone region/CALL SBI operation must complete on the FPGA (and the UART RX
loss makes automated entry flaky). Both are the monitor/RTL owner's domain. The
boot route is solved and repeatable; the corrected built-in image (`1d7a02e4…`)
and DTB are staged at `/tmp/capstone-b/fpga-image/` and `~/capstone-b-artifacts/`.
