# Plain twin of the 48 KiB / 12-way L1D (2026-11-24)

The semantics owner asked for it. A larger L1D is judged as a PAIR against Capstone at matched cache, never on Capstone
alone. The lead's rule stands: the L1D is the same on RISC-V and on Capstone.

- Plain today: riscv-base 8db8f9cda, 32 KiB / 8 ways (`baseline_cv64a6_imafdc_sv39_config_pkg.sv:49-50`).
- Capstone today: P1 d83d3a633, 32 KiB / 8 ways (`capstone_..._config_pkg.sv:83-84`).
- Capstone 48 KiB: 0039e34f4 (branch p1-l1d48-12way), its readings in Addendum 224.

## The change

capstone-ariane branch `riscv-base-l1d48-12way`, commit 77937b4c8, parent 8db8f9cda. Two files, the same lines as
0039e34f4, applied by anchor (the files were not copied):
- the baseline config package: DcacheByteSize 32768 -> 49152, DcacheSetAssoc 8 -> 12;
- `wt_dcache_missunit.sv`: the victim LFSR's ways 12..15 fold onto 8..11. The anchor is the `repl_way` assign at :210
  on 8db8f9cda, the same line 0039e34f4 replaced.

A script checked that the missunit +/- lines are byte-identical to 0039e34f4's. The submodule pins (19 gitlinks)
equal 8db8f9cda's. The way-count audit was re-read on the stock files (commit message): the index width is unchanged
(12), rd_hit_idx and inv_way are lzcs over 12 ways with padded leaves, and every way-sized array is parameterised.

## Gates

The baseline tree has neither the fork's lint gate nor its 95-test sweep, which needs the Capstone ISA. The Plain
gates run PAIRED, 8db8f9cda against 77937b4c8, each tree in its own worktree, with its own model built from a clean
`work-ver`:

1. **Lint:** the fork gate's whole-design invocation and counters (`rtl-lint-gate.sh`), target
   baseline_cv64a6_imafdc_sv39, with no Anvil section. The listing counts as VOID on any `%Error` or under 500 lines.
2. **Plain sweep:** riscv-tests isa `-p` for rv64ui / um / ua / uf / ud / uc / mi / si, run on both models and
   compared on result, RVFI trace and cycles.
3. **d12-set-stress-plain:** capstone-ariane `verif/tests/custom/capstone/d12-set-stress.S` (p1-l1d48-12way
   044d2ad60), with CAPPRINT defined as `addi t6, r, 0` and the values read from the RVFI trace. It is the only test
   here that fills a set past 8 lines and takes the fold.

## Pre-registered (written while the models build, before any reading)

1. **Lint:** every counter equal on the two trees. The fork's own port moved none (P1-line REF unchanged by
   0039e34f4). A by-name diff of the warning lines, with line numbers stripped, shows nothing new.
2. **Sweep:** the same pass/fail set on both trees, RVFI value-identical. Cycles are predicted identical: the
   tests fit in 32 KiB, as the fork's 95-sweep read identical cycles at 8 and 12 ways.
3. **d12:** checksums 0x2a81c / 0x3fc42 / 0x4514e / 0x7f914 on both trees, and the trap count is 0. A wrong checksum is
   data corruption and withdraws the port.
   - N=8 cycles are about equal on the two trees.
   - N=13 and N=24 miss on both.
   - N=12 is where Plain should DIFFER from the fork's reading. On Capstone the rev-node pool header (0xBFF00000)
     takes a way of set 0, so N=12 was 13 lines and read 1,569, not about 969. Plain has no rev-node unit. If no other
     line the program loads indexes to set 0, the timed passes at 12 ways are all hits: about N=8 x 12/8. On 8 ways
     they miss, several times higher. A reading well above x 12/8 means another line shares the set, and it would
     be explained before the hash is handed over.

## Readings (2026-11-24), graded against the pre-registration above

Both models were built clean (`rm -rf work-ver`, target baseline_cv64a6_imafdc_sv39, no extra defines), in their own
worktrees, dirty=no: base 8db8f9cda, port 77937b4c8. The branch tip is bb56087ba: a test commit on top, with core/
identical to 77937b4c8.

1. **Lint: as predicted on every gate counter.**
   - Both trees: LATCH 41, MULTIDRIVEN 0, ALWCOMBORDER 0, COMBDLY 0, UNOPTFLAT 33, BLKSEQ 1, UNDRIVEN 26,
     UNUSEDSIGNAL 269, CASEOVERLAP 0, SELRANGE 76. No `%Error`; listings of 4,048 and 4,084 lines.
   - The by-name diff (line numbers stripped) has 7 new lines and 4 renamed ones:
     - 4 width lines in the fold's arithmetic (missunit, `rnd_way` against the 32-bit compare);
     - 3 width lines at `perf_counters.sv:130` (below);
     - 4 renames whose bit ranges follow the way count (`dcache_data`, `wbuffer_check_mux`, `wbuffer_dirty_mux`,
       `miss_vld_bits_i`).
   - Nothing else.
2. **Plain sweep: as predicted.** 124 tests: riscv-tests isa `-p` rv64ui / um / ua / uf / ud / uc / mi / si (123), plus
   d12.
   - 122 pass on both trees. rv64mi-access and rv64mi-breakpoint fail on both (tohost 2 at 539 and 568 cycles): stock
     CVA6, the same on the two trees.
   - Per test, the loaded images are identical (objcopy). 123 of 124 are identical in result, RVFI trace and cycles.
   - The one that differs is d12, the test built to differ, which also shows the comparator fires.
3. **d12-set-stress-plain:**

   | cycles over 8 timed passes | N=8 | N=12 | N=13 | N=24 |
   |---|---|---|---|---|
   | 8 ways (8db8f9cda) | 553 | 1,035 | 1,221 | 2,350 |
   | 12 ways (77937b4c8) | 553 | 780 | 896 | 2,170 |

   - Checksums 0x2a81c 0x3fc42 0x4514e 0x7f914 on both trees; trap count 0.
   - N=8 is equal. N=12 at 12 ways is 780, below 553 x 12/8 = 830: all hits, as predicted for Plain (no line of the
     program shares set 0).
   - **Missed:** the 8-way N=12 is 1.33x the 12-way, not "several times". The stock testbench has no memory-delay knob
     (`S12_MEM_DELAY` exists only in the fork's testharness), so a miss is a zero-latency fill. The fork's 2.4x was read
     at delay 12. The direction and the checksums are what this run can grade.

**Found by the lint diff: HPM event 18 (L1D eviction) is wrong on every 12-way build.**
- `perf_counters.sv:130` (fork :136) compares the 12-bit valid bits with `8'hFF`, zero-extended to 12'h0FF. At 12 ways
  it counts misses with ways 0..7 valid and 8..11 invalid, and never a miss with all 12 valid.
- It affects 0039e34f4, b1-l1d48 6438348ec and 77937b4c8.
- It retracts the 0039e34f4 audit's "no hard-coded 8-way width ... perf_counters.sv". That claim was on the
  capstone-ariane lane branch only, not on dev.
- It is a counter only: no value, cycle or timing effect.
- The semantics owner checked: no reading on spec-silicon uses event 18 on a 48K build (Addenda 213 / 224 / 225 read
  event 2 / hpm8), so nothing is voided.
- Ruled: perf_counters stays untouched in this port, so the pair stays matched to 0039e34f4. The fix,
  `&miss_vld_bits_i[k]` (equal at 8 ways), goes into both lines together in a later build.

**The LUT key was mis-scoped, not missed by the build.**
- The band carried over the Capstone twin's measured delta (0039e34f4: placed 191,825 vs 187,368). The Capstone D$ carries
  per-way capability-tag state that the Plain D$ does not.
- The board lane's per-module split (both routed hierarchical reports) puts the change inside the cache subsystem:
  wt_cache_subsystem +996 LUT and +12 RAMB36.
  - wt_dcache_mem +515 LUT, RAMB36 24 -> 36: each data bank 8 -> 12 RAMB36, and four new tag SRAMs, gen_tag_srams[8..11].
  - wt_dcache_missunit -1,051 and wt_axi_adapter +1,556. The adapter's source is unchanged, so this is logic moving across
    the boundary, inside the per-module floor.
  - No module outside the cache subsystem moves by 150 LUT or more.
- That is a 12-way WT D$'s footprint, and simulation shows 12-way behaviour (d12 N=12: 780 vs 1,035 cycles). So nothing
  points to missing logic.
- **The seal is a valid matched Plain bitstream.** The semantics owner pairs it, on board 3, with 0039e34f4's readings
  (Addendum 224): Plain mcf, gcc train01 and nab, on the same stages and kit as Addendum 208's matched-Plain rows, with
  only the bitstream changed.
