# B5b-2 synthesis-only gates, steps 1 to 6 and CCSRRW on the tip: board lane readings (2026-11-24)

The board lane ran these gates on apollo at the rtl lane's request. They are recorded here with their identities. The
keys, predictions and verdicts on fix branches belong to the rtl lane, and each was pre-registered on llvm-capstone
`land/rtl-b5b2-plan` (`capstone/docs/plans/2026-11-24-b5b2-trap-route.md`) before its request. The B5b-1 gates before
these are in `2026-11-23-b5b2a-life-gate.md`.

**Method (every gate):**
- `synth/twc/<step>/post-<step>.sh SHA40 TAG` gates the launch on `mem-headroom.sh 44 16`.
- It runs `synth_design` only, under `vivado-guard.sh` at 40 GB, with the srcwatch and the loops-only in-flight gate
  against the base's gate.
- It keeps the synthesis checkpoint as `twc/gate-synth-<tag>.dcp`, then runs LUTLP and `rc-keys.tcl` (loops-only) on
  the trial and on the toy loop control, and grades.
- Guard exit 143 comes after `gate.done`: it is the chain stopping the run once synthesis has written its checkpoint.
- Every grader is derived from the previous one by asserted substitutions.
- **Grader controls before each launch:** the base against itself must read PASS 3/3, and the base with core LUT
  raised to the limit + 1 must read KEY3 FAIL. Both held for every grader below.
- **The keys (all gates):**
  1. technology-mapping peak within ±505 MB of the base's, under the 40 GB guard;
  2. 'Found timing loop' 0, check_timing loops 0 with the toy firing, LUTLP-1 0 with the toy firing, and the in-flight
     gate PASS. Synth 8-326 is keyed from the CCSRRW gate on. **Correction (2026-11-24):** this line used to list it as
     keyed for every gate, but the graders for steps 1 to 6b only read it in the .vds and printed it. Every one of those
     .vds files reads 0 (re-counted), so no verdict changes;
  3. core (i_cva6) LUT at most the base + 2,500.
- Every other row is reported against the ±2,500 redistribution floor or the rtl lane's band, and graded nothing.

## The dyn_unit / rev_node swing is the scoreboard-entry cone moving between them

instance's primitives by REF_NAME, and its LUT and FF cells by name stem, with bus indices and replica suffixes
stripped.
- `analyze.py` treats a missing marker as an error. Its NO-DATA test is anchored to line start, because Vivado's batch
  log echoes the Tcl source.
- `item3.tcl` lists the hierarchical pins on each top stem's nets.
- Control: 218 stems that sit in one module in all three checkpoints read a cross-module move of 0.

**Steps 1+2 -> 3+2b -> 4:**

  rows swing by about 4,400 each.

  For example, ra_data is 2,930 / 2,016 / 3,417 in dyn_unit and 0 / 1,319 / 0 in rev_node.

## Gate 6b's RAMB36 +2 is the epoch memory, which 6a had reduced to one live bit

**Instruments.** Read-only Vivado on the 6a and 6b checkpoints, 12 GB guard, every run exit 0.
- `twc/pairdiff/bram.tcl` counts RAMB primitives under i_adapter by memory.
- `epmem.tcl` lists each twc_ep_mem block's widths and its data, enable and address pins, live or tied to a constant.

**Per memory:**

| memory | 6a | 6b |
|---|---|---|
| tbm_mem | 7 RAMB36 + 1 RAMB18 | the same |
| twc_atag | 7 RAMB36 + 1 RAMB18 | the same |
| twc_data | 32 RAMB36 | the same |
| twc_ep_mem | 2 RAMB36 | 4 RAMB36 |

- The .vds RAM map rows are identical in both (twc_ep_mem 16K x 8, 4 RAMB36). The difference arises after the map.
- **Ports, the same shape in both:**
  - true dual-port 16K x 2 blocks;
  - writes on port A (3 live WEA pins; port B's enable tied off), reads on port B;
  - 14 live address pins on each port.
- **Live data bits:**
  - 6a: block 0 has 1 live write-data pin and block 1 has none; each has 2 live read pins;
  - 6b: each of the 4 blocks has 2 live write-data and 2 live read pins, i.e. all 8 epoch bits.

**Why.**
- The gate build defines `CAPSTONE_TWC_FILL_TARGETED` (`capstone_cv64a6_imafdc_sv39_config_pkg.sv:64`, on unless
  `CAPSTONE_NO_TWC_FILL_TARGETED`). On eff52e152 that compiles out the only bump of the current epoch `twc_ep_q`, the
  fill's clear.
- 6a's .vds records the consequence: Synth 8-3333 propagates constant 1 across `twc_ep_q_reg[0]` and constant 0 across
  bits 1 to 7. Every written epoch is then `twc_ep_q` or 0.
- 0c9992bc6 adds a bump on CPTAG's clear (`wt_axi_adapter.sv:535-543`, under `CAPSTONE_SUBLET_FMT`, outside the
  FILL_TARGETED ifdef). `twc_ep_q` becomes a live 8-bit counter, and 6b's .vds has no constant line for it.
- So the +2 comes from the epoch bump, not the third write source into tbm_mem, whose blocks are unchanged.
- The driver cells' names in the checkpoints are generated by synthesis and are not read here.
