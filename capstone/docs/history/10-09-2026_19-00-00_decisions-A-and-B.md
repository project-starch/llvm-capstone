# Decisions A and B, 2026-09-10 — reclaiming a revoked region, and what `end` means

Two decisions taken the same day, on the same pair of RTL fixes (R-30, R-31). **A** is about the
firmware that must ship with them; **B** is about the arithmetic the two documents use to describe
the same machine. Both are ruled. What remains open in each is push access, not judgement.

---

# Decision A — reclaiming a revoked region

## The problem: the RTL fix breaks the firmware unless they ship together

R-30 + R-31 change what `REVOKE` returns. The monitor already has code that reacts to that return
value, and today it never runs.

```
   FLASHED SILICON (the defect)              AFTER R-30 + R-31 (the fix)
   ────────────────────────────              ───────────────────────────
   REVOKE -> LINEAR                          REVOKE -> UNINIT, cursor at base
        │                                         │
        ▼                                         ▼
   monitor's "is it UNINIT?" guard           guard FIRES  ->  calls INIT
        │  never fires                            │
        ▼                                         ▼
   INIT never called                         INIT sees cursor == base
        │                                         │  (amended INIT needs cursor >= end)
        ▼                                         ▼
   ✅ path works                              ❌ FAULT — a working path breaks
```

**So the pair must never ship RTL-only.** That is the whole reason a firmware half exists.

## Why fill in the monitor, and not the two alternatives

```
  refuse the re-share  ─── closes nothing, only defers the cost           ✗
  fill lazily in the domain ─ safe ONLY if every domain fills before      ✗
                             reading. The hardware check that would
                             catch a read of unfilled memory is gated on
                             a privilege level domains never run at, so
                             THAT ENFORCEMENT DOES NOT EXIST.
  fill in the monitor  ─── the only option that closes anything, and      ✓
                          the only one whose correctness is local
```

## The fix: one loop that zeroes AND positions the cursor

`STC` is the only instruction that advances an UNINIT cursor, and it requires `imm == 0`. So a single
loop does both jobs INIT needs done:

```
   region   ┌──────┬──────┬──────┬── … ──┬──────┐   4096 B = 256 × 16 B
            base                              end
   cursor   ▲
            │  stc x0, 0(cap)   ← zeroes 16 B and advances the cursor
            └──────────────────────────────────▶   × 256
   cursor                                      ▲   cursor == end → INIT accepts
```

Monitor commit **`0a5c3d9`**, all four checkouts byte-identical:

| | |
|---|---|
| sites | **5**, not the 2 first identified — the annotation branches share one hoisted site (REV_DEFAULT / BORROWED / SHARED / TRANSFERRED), plus `share_child_region`, ×2 in `region_de_linear`, ×1 in `split_out_cap` |
| loop bound | from `cap_end − cap_base`, **not** the cursor — a capability arriving with its cursor already at `end` then **faults on the first store** instead of running zero iterations and looking fine |
| trace tags | `RCLM` running count (every share) · `RCSH` shortfall · `RCPR` precondition trip |
| gates | host-call **12/12** (this suite reaches the site), linear/uninit corpus **7/7**, smoke, nullblk **3/3** |
| emulator | shipped with it — without the STC cursor advance the fill is a no-op under emulation |

## What it costs on silicon (boots sw52 + sw53, resident bitstream)

```
   fillcost   stc  · cincoffsetimm · addi · bltu     8,639 cyc  ┐
   fillnop    nop  · cincoffsetimm · addi · bltu     2,466 cyc  ┘ differ by ONE instruction
                                                    ─────────
   256 capability stores                             6,173 cyc  =  24.1 cyc / 16-byte store
```

A 4 KiB reclaim ⇒ **+3.6 % instructions, ~8 % of cycles** at speedtest1's measured CPI
(4.6–26.2 % across the full on-silicon CPI spread — it is CPI-sensitive, not simply "low").

Two things measured rather than assumed:

* **a warm region is not materially cheaper** (a second pass costs ≥ 87 % of the first), so the figure
  applies to the monitor's real case and is not a cold-start artefact;
* **it is not a capability tax** — a plain 8-byte `sd` on the same walk costs 23.1 vs `stc`'s 24.1,
  so it is the write-through drain **per store**, and the capability part is ~1 cycle in 24.

## Pre-flash control that worked

`RCLM:00000000` on every share, **9 of 9**. Zero reclaims — as it must be where the guard cannot fire
— and the counter's reporting path is now **proven readable on silicon**, which is the one property of
it that could not be tested after the flash.

## Open

Monitor `0a5c3d9` is **local only**. `project-starch/capstone-sbi` returns `403 Permission denied`
for this lane's credential (attempted and recorded, not assumed). Someone with write access must push
it before the flash.

# Decision B — what `end` means

## The problem: it was the wrong question, asked twice

It was put as *"is `end` inclusive or exclusive, project-wide?"* There is no project-wide
convention to rule on — **each document is internally consistent, and each has exactly one
instruction written in the other's arithmetic.**

```
   RTL     end = ONE PAST the last byte   (EXCLUSIVE)
           ├── LSU faults when ea + size > end          ✓ exclusive
           ├── SPLIT partitions [.., val) and [val, ..) ✓ exclusive
           └── INIT: "cursor <= end is illegal"         ✗ INCLUSIVE  ← the outlier

   spec    end = THE LAST byte            (INCLUSIVE)
           ├── prog-model: interval [base, end] closed  ✓ inclusive
           ├── SHRINKTO: end = cursor + imm - 1         ✓ inclusive
           └── 4 access bounds: [base, end - size]      ✗ EXCLUSIVE  ← the outliers
```

Asking it as one question produced a ruling of EXCLUSIVE (`d71d5007ee05`, 02:18) that had to be
**withdrawn the same day** — and one route proposed under it would have opened a one-byte hole on
the store path.

## The resolution: change no conventions, fix each side's outlier

```
   RTL     capstone_flu_unit.anvil    INIT      cursor <= end     →  cursor < end
   spec    mem-access-insn.adoc:39    LDC       end - CLENBYTES   →  end - CLENBYTES + 1
           mem-access-insn.adoc:93    STC       end - CLENBYTES   →  end - CLENBYTES + 1
           existing-insn.adoc:66      load      end - size        →  end - size + 1
           existing-insn.adoc:260     store     end - size        →  end - size + 1
           cap-man-insn.adoc:287      SHRINKTO  cursor + imm      →  cursor + imm - 1   ← FIFTH
```

**The fifth was missed, and the way it was missed is the point.** The sweep grepped for the *shape*
it had already found — `end - N]` — so a site writing the same error as `+ imm > end` could not
match. SHRINKTO's guard used an exclusive end while its own effect two lines later sets
`end = cursor + imm - 1`; the guard forbade shrinking to a region reaching the parent's last byte.
A check keyed to one spelling silently missing another, inside the fix for exactly that class.

> ⚠ **CORRECTED after an adversarial audit (2026-09-10, later).** Three claims below were wrong and
> are struck through where they appear: it was **five** sites, not four; the board **does** build the
> changed module; and aligning the access bounds does **not** make the spec and the RTL agree "byte
> for byte" — every instruction that takes or returns a bound *as a value* still differs by one,
> which is the direct consequence of each document keeping its own convention.

**What settles the direction is not argument — the spec already contained the correct form.**
`prog-model.adoc:289` bounds a 4-byte instruction fetch at `[pc.base, pc.end - 3]`, which is
`end - size + 1`. The four data-access rules were the outliers, not the fetch rule. Each of them
forbade **the last legal access in every region**, describing a machine one granule smaller than
the one being specified.

## Worked example — the two now agree on every ACCESS, for every size

An audit worked this algebraically rather than on one example, and it holds for **every** region
size K and **every** access width N, 4-byte scalars included: the RTL's `A + N ≤ S+K` and the spec's
`A ≤ end_s - N + 1 = S+K-N` are the same inequality. The `+1` and the `-1` cancel exactly.

**But "the same machine" was too strong**, and is withdrawn. Aligning the access *bounds* leaves
every instruction that takes or returns a bound **as a value** off by one, because that is precisely
what keeping two conventions means: `LCC`'s `end` query returns `S+K-1` in the spec and `S+K` in the
RTL; `SPLIT` at `val` puts byte `val` in the lower half in the spec and the upper half in the RTL;
`SHRINKTO imm` and `SEAL`'s minimum size differ likewise. Those are **read from source, not verdicts**
— they need directed tests before anyone calls them defects — but they mean the resolution is
**incomplete**, and completing it is a decision for the lead, not a lane.

A 64-byte region starting at `S`, filled with 16-byte capability stores:

```
            S      S+16    S+32    S+48    S+64
            ├───────┼───────┼───────┼───────┤
   spec     end = S+63  (inclusive)      bound [S, end-16+1] = [S, S+48]
   RTL      end = S+64  (exclusive)      LSU: ea+16 > S+64 faults  ⇒ [S, S+48]
                                                                    ▲ same four starts

   after the fill      cursor = S+64
   spec  INIT illegal iff cursor <= end  →  S+64 <= S+63  false  →  ACCEPTS ✓
   RTL   INIT illegal iff cursor <  end  →  S+64 <  S+64  false  →  ACCEPTS ✓
   QEMU  exclusive throughout, faults iff cursor < end            →  ACCEPTS ✓
```

## Two things deliberately NOT changed

| | why |
|---|---|
| **`INIT`'s spec condition** (`cursor <= end` is illegal) | Correct **as is** under an inclusive `end`: a filled region leaves the cursor at `end + 1`. It would only move under the full-exclusive route, which was not taken. An RTL comment on the branch still says it "must be amended in the same change" — that sentence was written under the withdrawn framing and no longer applies. |
| **sealed-capability bounds** (`base + n·CLENBYTES − CLENBYTES`) | Base-relative, and already naming the last legal start. Nothing to fix. |
| **`SPLIT`'s half-open notation** (`cap-man-insn.adoc:302`, `:328`) | A notation question, not this one. Left for its own look. |

## The route that must stay refuted

```
   ✗ move the RTL's store bound to  end - 15
       correct for the spec's INCLUSIVE end …
       … but under the RTL's EXCLUSIVE end it permits a 16-byte store at end-15
         whose last byte lands AT end  →  ONE BYTE PAST THE REGION, on the store path
```

It is the right fix for the spec and **only** for the spec. With it excluded, no unsafe outcome
remains among the live routes.

## What landed

| half | where | state |
|---|---|---|
| RTL | `r30-r31-init-revoke` `1bfff7776` (`flu:176` now `cursor < end`) | **pushed** |
| spec | `capstone-academic-spec` `caplifive-s06` `21a01f0` | local — remote 403; **this is the authoritative spec** |
| spec | `capstone-spec` `caplifive` `230418b` | local, and **deliberately left unpushed** — the lead is archiving that submodule, so the mirror commit is moot |
| QEMU | `c128-qemu-merge` `72fb56be86` — `csinit` faults iff `cursor < end` | **pushed**, parent points at it |

**Both spec checkouts were edited before the archive decision, and that was the right call at the
time:** `mem-access-insn.adoc` and `existing-insn.adoc` were byte-identical between them, so fixing
one would have left the two trees disagreeing on exactly the lines under discussion. With
`capstone-spec` now being archived, `capstone-academic-spec` is the authoritative one and the mirror
commit simply stays where it is.

## A consequence that is now settled rather than "narrows"

```
   QEMU csinit keeps  cursor == end   →  accepts one value, RTL accepts end and above
                                         sets still differ above end   →  Q-07 NARROWS
   QEMU csinit takes  cursor >= end   →  both hold end exclusively
                                         sets are IDENTICAL            →  Q-07 CLOSES  ✓
```

The Q-07 change as written takes the second, so Q-07 closes.

## Open

Both spec commits are **local only** — `project-starch/capstone-academic-spec` returns
`403 Write access not granted` for this lane's credential, the same as `capstone-sbi`. The parent's
submodule pointers are therefore **deliberately unmoved**: bumping one would make the parent
reference a commit that does not exist on its remote.

# Appendix — the CMA change's execution evidence (gathered 2026-09-10, no merge required)

The CMA PR was held into `dev` for want of execution evidence. Here it is, gathered **without
merging anything**, which is worth recording as a method: the PR adds a `--kernel-arg` option to
`run-domain-smoke.py`, and it is not needed. The committed runner already has `--qemu-extra-arg`,
appended **verbatim at the very end** of the qemu command line (`run-domain-smoke.py:276`), and qemu
takes the **last** `-append`. So a second `-append` passed that way overrides the built-in one, and
the evidence does not depend on the change under review.

```
   build control ── the rebuilt QEMU kernel carries CMA          5 symbols in linux-custom/.config
                    (linux-6.1.26 beside it is the SOURCE tree
                     and has none — a `linux-*` glob picks that
                     one first and reports "no CMA" on a kernel
                     that has it)

   run A   cma=256M     cma: Reserved 256 MiB at 0x00000000f0000000
                        Memory: … 262144K cma-reserved            ✓
   run B   no flag      (no reservation line at all)              ✓
                        ────────────────────────────────────────
                        the flag is what reserves the area — the control DISCRIMINATES
```

**Both halves of that were needed.** Run A alone cannot distinguish "CMA works" from "this kernel
always reserves something"; run B is what makes A mean anything. Two earlier attempts produced
`0` reservations in *both* runs for reasons that had nothing to do with CMA — argparse rejecting a
bare `-append` as an option-shaped value (exit 2 in zero seconds), and then both runs writing to the
runner's **default** log file so the comparison was between one transcript and itself. The check
reported NOT DISCRIMINATING each time rather than reading the shared zero as a result.

**Landed** as `3a20a7712fc6`, moving both buildroot pins in one commit after the submodules were
pushed.

> ⚠ **"The board's build is unchanged" was WRONG as I wrote it, and is corrected here.** What is
> unchanged is the board's **kernel config**: `fpga_defconfig:19` reads `fpgakernel.config`, which
> gained no CMA, so `dma_alloc_contiguous()` returns NULL and `__dma_direct_alloc_pages` falls
> through to the same order-rounded buddy allocation with the same 4 MiB ceiling. **But the board
> builds the changed MODULE** — `fpga_defconfig:42` has `BR2_PACKAGE_MODCAPSTONE=y`, and five of the
> merge's six files are under `package/modcapstone/`. Three board-visible consequences follow, none
> of them yet exercised on silicon:
>
> * `GFP_HIGHUSER` → `GFP_KERNEL` was **forced**, not cosmetic: `dma_alloc_pages` has
>   `WARN_ON_ONCE(gfp & __GFP_HIGHMEM)` and returns NULL, so the old flags would have failed every
>   allocation.
> * **The zeroing extent shrank.** The old `__get_free_pages(… | __GFP_ZERO, order)` zeroed all
>   `2^order` pages; `dma_direct_alloc_pages` memsets only `PAGE_ALIGN(len)`. For a 3 MiB request
>   that leaves 1 MiB of the 4 MiB allocation unzeroed. **Not an exposure** — the monitor carves
>   exactly `[base, base+len)` and `device_mmap` bounds every mapping by `regions[i].len` — but the
>   claim "zeroing survives dropping `__GFP_ZERO`" is true of the fact and wrong about the extent.
> * A new hard-failure mode: if `platform_device_register_simple` fails, `region_dev` is NULL and
>   every region creation fails.
>
> **The last board image predates the merge** (`build-fpga` artifacts 2026-09-10 18:23, merge 18:57),
> so it contains the OLD module. The next `make TARGET=fpga` ships the new one, untested on silicon.
> A smoke run before the next measurement boot is the cheap way to close that.

# Appendix — SPLIT's cut side, settled by SIMULATION rather than by reading two sources

The `end` resolution aligned every ACCESS bound. It left the instructions that take or return a
bound **as a value** differing by one, and `SPLIT` is the sharpest of those because it is not a
readback — the same call produces a different partition. That had been a reading of the spec against
the anvil source. It is now a measurement: `verif/tests/custom/capstone/split-cut-side.S`
(`capstone-ariane` `ec320921e`), run on `capstone_cv64a6_imafdc_sv39`, 386 cycles against a
2,000,013 timeout — a real completion, not the harness's SUCCESS-at-timeout.

**Provenance, because it decides what the number measures.** The sim ran on the working tree at
**`62b09ca92`** (branch `s12-ldc-rolling-filter`), *not* on `1bfff7776` where the R-30/R-31 fixes
live. Those two differ by 27 lines in this very file, so the result would not automatically carry
across — it was checked rather than assumed: **the SPLIT block is byte-identical between them**, and
the working tree had no uncommitted RTL edits. The finding holds for both revisions.

```
   one linear capability, base 0x80001000, split at val = base + 64 = 0x80001040

   Reg[11]  lower half   Start 0x80001000   End 0x80001040   Type 1  Perm 7  Revnode 2
   Reg[16]  upper half   Start 0x80001040   End 0x80001100   Type 1  Perm 7  Revnode 3
                               ▲
                               └── val is the upper half's FIRST byte
```

**On silicon, byte `val` lands in the UPPER half.** The RTL's `end` is exclusive, so the lower half
is `0x80001000 .. 0x8000103F` and does not contain `val`; the upper half starts *at* `val`. The two
are contiguous with no gap and no overlap, so the RTL is self-consistent.

**The spec describes the other partition.** `cap-man-insn.adoc:338`: `x[rs1].end := val` — inclusive,
so byte `val` is in the LOWER half — and `x[rd].base := val + 1`. Also self-consistent, also
gapless. Just one byte across.

```
   spec   [base … val]      [val+1 … ]      val in the LOWER half
   RTL    [base … val-1]    [val   … ]      val in the UPPER half   ← what the hardware does
```

**Why this is not the "notation question" it was dismissed as.** Software written from the spec that
splits at `val` expecting `val` in the lower half gets it in the upper half on real hardware. That is
a semantic difference in what the instruction does, not a difference in how a closed interval is
written. It also confirms, incidentally, that SPLIT allocates a fresh revocation node for the upper
half (2 → 3) and preserves type and permissions.

**Not urgent, and here is the honest reason:** nothing we build reads bounds from the prose. The
monitor and the compiler take them from the RTL via `__capfield`, so they agree with the hardware,
and access enforcement — the half that governs safety — now agrees exactly. The exposure is to a
future implementer or a reader working from the spec. But it should not be left undecided
indefinitely, and it is the lead's, because whichever way it goes one of the two documents changes.

The other three (`LCC`'s `end` query, `SHRINKTO`'s size, `SEAL`'s minimum) follow mechanically from
the two conventions and are still source readings, not measurements. Each would take a test of this
shape.
