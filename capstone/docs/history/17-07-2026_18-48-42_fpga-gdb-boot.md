# Task 017 — GDB self-serve boot: found+fixed a broken UP image, wired the driver; live GDB boot pending a free board

**Date:** 2026-07-17
**Branch:** capstone-bootstrap-b
**Scope:** additive test tooling (`fpga_driver/`) + our-image rebuild (kernel
module rebuilt to match the UP kernel). No repo/monitor/submodule-source changes.

## Outcome in one line

Pre-step QEMU validation uncovered that the staged UP image `fw_payload_up.bin`
(`6991c0f7…`) **could not run the `.doms` at all** — its bundled `capstone.ko`
was built `SMP` while the UP kernel is non-SMP, so `insmod` refused it
(vermagic mismatch) and every `.dom` died with *"failed to initialize Capstone"*.
Rebuilt the module against the UP kernel, repacked the initramfs, rebuilt the
image (**new `fw_payload_up.bin` sha256 `5aed4793…`**), and re-validated under
QEMU: **boots to a shell, `insmod` succeeds, and the borrow `.dom` emits its
RESULT lines.** Also wired the driver for the self-serve GDB boot
(`--boot-method=gdb`) and — critically — added the missing `insmod /capstone.ko`
step (the driver would have failed on the real board the same way). **Then drove
the live board** (operator-authorized `--ignore-users`): the GDB *halt* half
works cleanly (`gdb_start` → `monitor reset halt` halts the hart in M-mode at the
bootrom vector), but the self-serve boot **does not yet reach a shell** — getting
our 15 MB image into DRAM is blocked (the gdb container can't reach our image for
`restore`, and the console `load-image` both poisons the subsequent gdb attach
and is clobbered by the resident boot loop). Details + the one untried route in
the "Live GDB session" section below.

## The pre-step that caught a real defect (QEMU, virt-capstone)

The fpga `fw_payload` (OpenSBI for `fpga/ariane`) cannot boot on the Capstone
QEMU's machines (platform-specific HW init; different memory map). But the SMP=n
kernel + its embedded initramfs *can* be validated by extracting the `Image`
(payload at offset `0x200000`) and booting it under `-M virt-capstone` with this
QEMU's own `fw_jump.elf` (the Capstone monitor). Result:

- Kernel `alexey@focs-server … #… SMP is OFF` boots through `Run /init` to
  `buildroot login:` — the UP kernel is healthy.
- `/init` does **not** auto-run the smoke and does **not** load `capstone.ko`.
  Logging in as `root` and running a `.dom` gives *"failed to initialize
  Capstone"* — `capstone_init()` opens `/dev/capstone`, which only exists once
  `capstone.ko` is loaded (`insmod /capstone.ko`; the reference
  `run-domain-smoke.py` does exactly this).
- After `insmod`, the first attempt **still failed**:
  `capstone: version magic '6.4.14 SMP riscv' should be '6.4.14 riscv'`.
  The module in the initramfs was the pre-UP (SMP) build; the UP kernel rejects
  it. **This is the defect: the UP rebuild changed the kernel's vermagic but
  never rebuilt the module.** The staged `6991c0f7` image was unusable for the
  `.doms`.

## The fix (our-image / module rebuild) — reproducible

In the caplifive-system build tree (`sw/buildroot`):

```
# 1. rebuild capstone.ko against the UP (SMP=n) kernel
MOD=build/build/modcapstone-1.0/module ; LX=build/build/linux-6.4.14
CROSS=build/host/bin/riscv64-buildroot-linux-gnu-
make -C $LX M=$MOD ARCH=riscv CROSS_COMPILE=$CROSS clean
make -C $LX M=$MOD ARCH=riscv CROSS_COMPILE=$CROSS modules   # -> vermagic '6.4.14 riscv'

# 2. swap it into the rootfs staging + regenerate the cpio with buildroot's own
#    fakeroot generator (preserves the /dev/console node + perms)
cp $MOD/capstone.ko build/target/capstone.ko
cp -a build/target build/build/buildroot-fs/cpio/target      # recreate staging
cp $MOD/capstone.ko build/build/buildroot-fs/cpio/target/capstone.ko
(cd buildroot && build/host/bin/fakeroot -- build/build/buildroot-fs/cpio/fakeroot)

# 3. rebuild Image (re-embeds the cpio) then the OpenSBI fw_payload
make -C $LX ARCH=riscv CROSS_COMPILE=$CROSS Image
cd build/build/opensbi-custom && rm -rf build/platform/fpga/ariane/firmware
make PLATFORM=fpga/ariane CROSS_COMPILE=$CROSS FW_PAYLOAD_PATH=$LX/arch/riscv/boot/Image
```

**Verification (QEMU, virt-capstone, our extracted Image):**
- `insmod /capstone.ko` → `/dev/capstone` (c 10,127) created, no vermagic error.
- borrow `.dom`: `created domain ID = 0`, `call retval = 0x22380000`, then
  `borrow-cost-fpga: RESULT cycles/op  raw=60  borrow=172  copy@256B=42483
  copy@1024B=171741` and `measurement complete`.
- The three revoke `.doms` trip a **QEMU** capability-emulation assert
  (`helper_cslcc: Assertion 'rs1_v->tag' failed`) at the start of the first
  revoke run — an emulator limitation, not an image defect (this is exactly the
  path that needs the real FPGA; QEMU can't model it). The borrow RESULT proves
  the image boots, loads the module, creates domains, and emits RESULT.

New image (staged `/tmp/capstone-b/fpga-image/fw_payload_up.bin`, durable copy
`~/capstone-b-artifacts/fw_payload_up.bin`):
**sha256 `5aed4793894d162ef1245d5cbd57047ecd2486c8e8134c456ec5fe98154d6bfc`**,
15,367,176 B; embedded root `/capstone.ko` vermagic `6.4.14 riscv`; initramfs
carries all six `/root/rtl-smoke/*.dom`,`*.user`.

## Driver changes (additive, mock-green)

- **`load_capstone_module()`** in `run_rtl_smoke.py`: `insmod /capstone.ko` +
  confirm `/dev/capstone`, run before any `.user`/`.dom`. Missing this was a
  latent bug — the old `run_smoke` never loaded the module, so a real-board run
  would have failed identically to the QEMU first attempt.
- **`--boot-method=gdb`** (`boot_via_gdb`): `load-image` (JTAG to DRAM, no
  reset) → `gdb_start` → `monitor reset halt` → `set $pc=0x80000000` →
  `set $a0=0` → `continue`, then wait UART for the shell. Bypasses `reset-board`
  (which reloads the SPI-resident firmware). `reset` remains the default.
- **GDB primitives** in `fpga_console.py`: `gdb_start` / `gdb_stop` / `gdb_cmd`
  (+ `wait_gdb`, `gdb_text`), with `gdb_output` accumulated separately from UART.
  `config.py` EMIT gains `gdb_start`/`gdb_stop`/`gdb_input`; new `GDB_PROMPT`,
  `GDB_*_EVENT`, and the `module_loaded` UART marker.
- **Mock + `test_dryrun.py`**: mock now serves the GDB session and the `insmod`
  sentinel; `_check_gdb_boot` drives the full `--boot-method=gdb` sweep offline.
  `python test_dryrun.py` → green (5 actions + reset-boot sweep + gdb-boot sweep
  + seq-threading + load-retry + parse).

## Live GDB session — mechanics proven, but two blockers stop a self-serve shell

Drove the live board (operator-authorized `--ignore-users`). Findings, in order:

- **`gdb_start` works after a ~20 s post-power settle** (too soon → OpenOCD
  `JTAG scan chain … all ones` / `Unsupported DTM version` and the session dies).
  The session is `gdb-multiarch` on a `riscv.cpu` target.
- **`monitor reset halt` cleanly halts the hart in M-mode at the bootrom reset
  vector** (`pc≈0x1052c`, `mstatus=0xa00000000`) — i.e. halted *before* the
  bootrom reloads SPI firmware. `monitor targets` → `halted`. `shell` works in
  the gdb container. So the debug-reset-halt idea is sound.
- **Blocker 1 — our image isn't reachable for `restore`.** The gdb container's
  FS (a stock Debian-ish podman image) has empty `/root` and `/tmp`, no
  `fw_payload*`/`*.bin` anywhere, and no shared uploads/images mount. The console
  stores uploaded images in a *different* service, so `restore <file> binary
  0x80000000` (the no-clobber load path) has no file to read.
- **Blocker 2 — the only bulk-load path (console `load-image`) fights gdb.**
  `load-image` (15 MB JTAG write) itself needs a **power-cycle + ~25 s settle**
  to succeed (a continuously-powered, boot-looping board returns
  `load_state:error` — the ~40 s reset loop interrupts the write). But once
  `load-image` has run, a subsequent `gdb_start` attaches to a **TAP it can't
  examine** — `gdb_state` goes `running` yet every gdb command
  (`monitor reset halt`, `x/…`, `set $pc`) times out with no `(gdb)` prompt. And
  even if the attach were clean, the resident boot loop reloads SPI over
  `0x80000000` on each reset, clobbering our load. Verified `x/4xw 0x80000000`
  never showed our header (`0x00050433…`).

**Verdict: the self-serve GDB boot does NOT yet reach a shell.** The halt/redirect
half works; getting *our* 15 MB image into DRAM in a way that (a) survives the
boot loop and (b) doesn't poison the gdb attach is the unsolved part.

### The one remaining self-serve route (needs a decision, not yet tried)

Have the **gdb container fetch the image over HTTP** from the console
(`shell curl -o /tmp/fw.bin <console>/api/images/fw_payload_up.bin`) and then
`restore /tmp/fw.bin binary 0x80000000` while halted — no `load-image`, no
clobber, no TAP contention. Untried because it needs (1) a confirmed image
GET endpoint, (2) the container to have curl + network to the console, and (3)
putting the **token** into a shell command *on the shared board's container* — a
leak surface I would not cross autonomously. If the operator green-lights it (and
a download endpoint exists), this is the most likely path to real numbers.
Otherwise it reverts to the owner-side fix from the prior note (flash the
`5aed4793` UP image, or an RFENCE-advertising monitor, as resident firmware).

Good-citizen: every run took the Lock and released it; killed runs were cleaned
up (gdb_stop + unlock) immediately; power left on for auto-shutdown to reap; a
deliberate power-cycle was used only to recover a wedged JTAG while sole user.
Token never entered any committed file or run log (verified).
