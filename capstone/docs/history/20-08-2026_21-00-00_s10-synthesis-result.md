# S-10 synthesis: memory is fine, timing regressed 5.8 ns, and the cause is not the fix's own logic

**Date:** 2026-08-20
**Build:** `capstone-ariane` `80843404c` (S-10 fix merged at `3d3ed1502`)
**Artifact:** `synth-80843404c-exit0.tar.gz`, 93 files, collected automatically
**Reference:** `e1140aeea` — the previous build, differing by ONE file (`wt_dcache_mem.sv`)

## The question that was asked: memory. Answered, no.

```
exit=0   elapsed 01h45m10s   peak RSS 21.53 GB   (guard ceiling 40 GB)
reference e1140aeea:         peak RSS 20.94 GB   1h48m
```

**+2.8% memory, 3 minutes faster.** Nowhere near the kill criterion (~42 GB) or the ceiling.
The `>100 GB` / `343 GB` failure mode did not recur and was never close.

## The three falsification checks

| check | predicted | measured | verdict |
|---|---|---|---|
| `i_wt_dcache_mem` LUTs | 1206 → ~1306 | 1206 → **1262** (+56) | **HELD** |
| `check_timing` loops | still **30** | **16** | **DEVIATED** — favourable direction, unexplained |
| loop warnings vs reference | unchanged set | count halved | see below |

The loop prediction was wrong. It was stated as *"if it returns 31, the analysis is wrong"* — 16 is
neither, and a deviation is a deviation regardless of its direction. It is not explicable by
62 lines added to one leaf module.

## Timing regressed, and it is real

```
                 e1140aeea        80843404c        delta
WNS              -10.629 ns       -16.400 ns       5.771 ns worse
TNS              -438,671         -860,429         2.0x
failing endpoints 96,727           102,774          +6,047  (+6.3%)
critical path    cur_idx_q_reg[1] cur_idx_q_reg[3] same register, different BIT
```

**Only `clk_out1` fails.** Every other clock is positive — `mem_refclk` +0.177, `freq_refclk`
+0.143, `sys_clk_p` +2.127, `eth_rxck` +4.907 — and the Inter Clock Table reports **zero** failing
endpoints in every row. The DDR PHY is not involved. (An earlier reading of "5 new DDR endpoints"
was a substring false match: `vaddr_to_be_flushed` contains `ddr`. The 5 MIG-sourced endpoints are
on `clk_out1`, the MIG's AXI user-interface clock.)

## The fix's own logic is NOT the critical path

```
WORST slack through the fix's nets   -11.201 ns
DESIGN WNS                           -16.400 ns
```

5.2 ns clear. Same conclusion as the S-07 fix drew last time (−6.196 against −10.629, 4.4 ns
clear). Removing the S-10 fix could not recover the 5.8 ns, because WNS is set by paths that do
not run through it.

## What actually explains the regression

The design grew far more than the change did:

```
i_wt_dcache_mem   1206 -> 1262      +56 LUTs      <- the change
ariane_xilinx   169415 -> 171161  +1746 LUTs      <- the design
device occupancy  83.1% -> 84.0%
```

**+1690 LUTs appeared outside the module that was edited.** Together with the loop count halving
and the critical path moving to a different bit of the same register, that is not the signature of
62 lines of added logic. It is the signature of **synthesis taking a materially different
optimisation trajectory** — a heuristic flow on an 84%-full device, with both `place_design` and
`route_design` on `-directive RuntimeOptimized`, tipped into a worse local optimum by a small
perturbation.

That is precisely the **second-order placement/congestion mechanism** the pre-run audit named as
the one residual risk it could not bound statically. It is now observed rather than hypothesised.

## The call that was got wrong

The `618f4ce36` control build was recommended AGAINST, on the grounds that the
`−6.196` vs `−10.629` measurement had settled attribution. That settled whether the S-07 fix was
**on the critical path**. It did not settle whether adding logic **perturbs the design globally**,
which is a different question and is exactly the one now open.

**One run cannot distinguish** "this change costs 5.8 ns of WNS" from "any change to this design
costs about that much, because the flow is unstable at this occupancy". Only a control build can,
and it is now worth its 2 hours in a way it was not before — the cheapest version being
`618f4ce36` unchanged, or equivalently a rebuild of `e1140aeea` to see whether it reproduces its
own `−10.629`.

## Does this block a reflash?

Not on the evidence, but the margin narrowed.

The previous bitstream failed timing at −10.629 **and worked** — SQLite passed its correctness
suite on it. The dom-switcher cone is believed architecturally multicycle (open with the RTL
author). Under a two-cycle assumption:

```
requirement 40 ns, two cycles = 80 ns
e1140aeea:  path 50.6 ns   margin 29.4 ns
80843404c:  path 56.4 ns   margin 23.6 ns
```

Still fits, with 23.6 ns to spare. If the multicycle reading is wrong, the design was already
broken before this change and is now more so.

## A gap this run exposed in our own tooling

**The timing forensics peaked at 36.17 GB, and it runs UNGUARDED.** `collect_artifacts` is invoked
after the guard's monitoring loop has exited, so the enumeration — which opens a routed checkpoint
and materialises 100k timing paths — is outside the ceiling entirely. It came in under 40 GB by
luck, not by protection, and it is within a factor of two of the machine-killing territory this
whole apparatus exists to prevent. The collector should run its Vivado step under the same ceiling.
