# The cost of a capability copy through one stack slot: the DYN unit's one-op handshake, not the store buffer (simulation, 2026-11-04)

*The RTL lane, answering the SPEC lane. On silicon, devmk (+movc-keeps-integer-source) removes the compiler's "stc then
ldc of the same stack slot" pairs. On imagick that removes ~3 % of instructions and 10-12 % of cycles, on bitstream 3 and
ObjBounds alike (spec-silicon dd8bfa5e08cb, results/2026-11-03-eval/RESULT.md).*

The hypothesis on the table was a store-to-load hazard. The load unit has no forwarding: a load whose page offset [11:3]
matches any buffered store waits in WAIT_PAGE_OFFSET until that store drains (`store_buffer.sv` address_checker,
`load_unit.sv` IDLE). **For the capability pair that hypothesis is refuted.** The pair costs the same whatever slot the ldc
reads, and its ldc never enters WAIT_PAGE_OFFSET. Plain sd/ld pairs do pay the wait.

## The test

`stc-ldc-slot.S` has nine arms, -DSL=1..9. Each arm runs 512 iterations of `<body>; addi; bnez` and prints the mcycle
and minstret deltas, a value, and the trap count and cause. The hypothesis and the per-arm predictions are in its header,
pushed before the run (capstone-ariane objb-eval d463206ac).

The same blob (868111d4cd6e) is committed on all three trees:

| tree | commit | core |
|---|---|---|
| bitstream 3's tokens | c5a-eval-ctl 3afd5c9e2 | `CAPSTONE_NO_LIFETIME_CHECK` undefined |
| ObjBounds | objb-eval d463206ac | core = 603528b8b |
| C.5a | c5a-eval 08c9fbd22 | core = 1fc2cd5aa |

Run conditions:
- SUP_TRACE + R43_TRACE, memory delay 12, the model rebuilt for each tree;
- every PROVENANCE reads `rtl_dirty=no`;
- all 27 runs end `*** SUCCESS *** (tohost = 0)`;
- instret and every value are equal on all three trees.

## The mechanism, from the trace and the source

LDC and STC are `CAPSTONE_DYN` ops. The DYN unit takes one op at a time:
- its Anvil main loop (`anvil_build/capstone_dyn_unit.anvil`, `loop ep.flush`) raises `rtr` and receives an op;
- the LDC or STC thread hands the op to its syncer and waits for the LSU's answer (`recv cap_load_ri.res` /
  `recv cap_store_ri.res`), then sends the result and spends `cycle 1`;
- ex_stage registers the ready and masks it with the op in flight
  (`capstone_dyn_ready_o = !capstone_dyn_valid_i & capstone_dyn_ready_q & ~(|rev_drain_q)`);
- the issue stage sees it as `fus_busy.capstone_dyn` (`issue_read_operands.sv` `fu_busy` for `CAPSTONE_DYN`).

In the steady state of arm 2, every DYN op is dispatched 3 cycles after the previous op's result, on all three trees.
The result-to-commit gap is always 1 cycle, so timing alone cannot separate this handshake from a wait on commit; the
source names the handshake.

| tree | LDC: dispatch to result | STC: dispatch to result | iteration |
|---|---|---|---|
| b3 (includes the node query) | 6 | 8 | 20 |
| C.5a | 2 | 3 | 11 |

So by the time the ldc reaches the load unit, the stc has left the store buffer, and the page-offset compare never
fires. The earlier arcfour reading (dev 34c0483925f6, arm 3) shows the same: the ldc goes IDLE → SEND_TAG_LDC → IDLE on
both trees there too.

## What each RTL lever would buy (simulation cycles per pair, ObjBounds / C.5a)

Costs over the bare loop:

| pair | cycles over the loop |
|---|---|
| capability pair | 8.4 |
| plain pair, same slot | 6.3 (of which the page-offset wait is 4.0) |
| plain pair, different slots | 2.4 |

What each change saves:
- **Store-buffer forwarding alone:** nothing today, because the wait it removes never happens on this path.
- **A DYN path that overlaps LDC/STC** (pipelined, or the ops issued to the LSU like plain accesses): about 2.0 for the
  same-slot pair. The page-offset wait then appears in its place, as it does for the plain same-slot pair.
- **Both together:** about 6.0, which brings the pair to the plain different-slot cost.
- **On bitstream 3** the node query adds about 9 per pair on top of this (17.3 over the loop).

These are simulation cycles at memory delay 12, so they give a pattern, not silicon costs. They are consistent in order
with the silicon reading: devmk replaces each pair with a movc, and ~1.5 % pairs per instruction carrying ~10 % of
cycles is several cycles per pair. That consistency is only an order-of-magnitude check.

## What this does not settle

- The silicon per-pair cost was not measured. The devmk delta also includes every other change devmk makes to the code.
- Whether the 3-cycle gap is the `cycle 1` plus the registered ready, or partly a commit dependency, was read from
  source, not isolated by a variant.
- The pair inside real code (arcfour arm 1) did enter WAIT_PAGE_OFFSET, because byte stores were buffered ahead of the
  stc. In surrounding code with older stores, forwarding could matter even on today's DYN path. That case was not
  measured here.
