Two distinct allocations: (1) the Lua TvbRange userdata kept alive in the global
`ProtocolState` table, and (2) the separate 72-byte C tvbuff (g_malloc'd by
tvb_new_subset_remaining for the TCP payload). The C engine frees the tvbuff at
epan_dissect_reset -> tvb_free_chain; the surviving TvbRange still points at it,
so re-dissection feeds the dangling tvb into proto_tree_add_item_new ->
tvb_ensure_bytes_exist. NOT a borrowed pointer into a single Lua object.

The issue's reported crash is in tvb_offset_from_real_beginning, reached from the
SAME proto_tree_add_item_new use-site (tvb_raw_offset <- hfinfo_bitshift <-
proto_tree_add_item_new); 4.6.4's leaf within that add path is
tvb_ensure_bytes_exist. Same object, same free-site, same use-site.

===== B. CONTROL: trigger.lua, single-pass — clean =====
No tvb Invalid read. Each packet is dissected once: handle_packet() stashes the
range and it is used in the SAME call while its tvbuff is still live. Without a
second dissection there is no stale reuse.

===== C. CONTROL: trigger_fixed.lua, two-pass — clean =====
No tvb Invalid read. The fixed script fills the ProtoField from the CURRENT live
`buffer` on every dissection instead of caching a TvbRange, so no Lua handle
outlives its C tvbuff.

The differential (UAF only in A; clean in B and C) is what makes this a verified
reproduction rather than an incidental warning. Reproduced 2026-08-03.

Note: unrelated libre2/libsinsp "uninitialised value" warnings appear at epan
init (the bundled falco/sinsp plugin) in ALL three runs and are noise; the PASS
check keys on the tvb-UAF stack signature, not on valgrind's exit code.
