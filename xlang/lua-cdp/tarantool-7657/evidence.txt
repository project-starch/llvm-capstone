Interpretation: GC ran mid-iteration and collected an intermediate merge_source
cdata; lbox_merge_source_gc -> merge_source_unref dropped the refcount to 0 and
destroyed the C `struct merge_source`. LuaJIT's sweep zeroed the freed slab, so
the NEXT lbox_merge_source_gen read source->vtab->next as NULL and called through
it -> rip=0x0, cr2=0x0 (SEGV_MAPERR at address 0). This matches the upstream
report's `lbox_merge_source_gen+147` crash and its "merge source ... gc is called"
debug line at iteration 5312.

Determinism: 3/3 runs crashed (including the first), because the collectgarbage in
fetch_chunk pins the free to a mid-iteration point.

===== CONTROL: FIXED (2.11) — no crash =====
7000
docker exit code: 0

The fix (PR #7664, commit e52fabf9058453efc0661092822feff609615ef1,
"lua/merger: fix use-after-free during iteration"; backported to 2.10 as f9aecfb)
makes lbox_merge_source_gen return the SAME cdata that was passed in, instead of
minting a fresh un-ref'd cdata each step. Refcounting is then balanced, so the
merge_source is never freed mid-iteration and the script completes -> 7000.

The differential (SIGSEGV on 2.8.3, clean 7000 on 2.11) is what makes this a
verified reproduction rather than an incidental crash.
